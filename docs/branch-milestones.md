## ① LLM Wiki 编译链路（09-18）

**解决什么**：RAG 优化「能不能捞到」，但记忆是碎片、没有结构。这一步让零散记忆
变成**可读的知识库**——两级编译：会话内归纳成页 → 跨会话按主题聚合成实体页；
配套链接重定向、失败兜底与格式修复。**wiki 不反向改写记忆**（纯派生）。

**关键实测**：223 会话 / 1562 条记忆 → 第一级 **660 页** → 第二级 **20 域 / 233 页**
（压缩比 2.8:1）；链接死链 92.6% → **0%**。

**顺带发现的通用问题**：提示词里的"内容 ≤120 字"是软约束，**没有任何模型稳定遵守**
（超标率 24%~53%）→ 改为代码级硬截断；模型"返回了内容但 JSON 坏了"原先只能整条丢弃
→ 增加格式修复模型救回被截断的内容。

## ② 可运维的知识库（09-19）

**解决什么**：一次性脚本变不成系统。这一天补的是"长期运行需要的那些东西"：

- **它会知道自己过时了**：编译清单（输入指纹）+ 对齐审计（引用/覆盖/死链）
- **它能增量更新**：脏会话重编 + 脏域局部重编 + 链接修复 + 清单刷新；由**写入时
  触发器**驱动（时点档 / 脏记忆攒够 / 每日首写），不需要常驻调度器
- **它可回滚**：索引库整库 + wiki 产物目录**原子快照**（LLM 产物重编会漂移，
  反馈演化值更是无法重建）
- **它可运维**：失败清单跨次累积 + 定向补跑（CLI / HTTP / Python 同一份实现）
- **它接上了写入链路**：`memory_save` 直写的记忆此前对 wiki **完全不可见**，
  补齐落表 + 历史回填

**同时段的事故与加固**（详见架构文档 §12）：测试污染导致 79 个 L1 产物丢失（此后
测试禁止解析真实 wiki 目录）；L2 混版（此后全量重跑统一版本 + 自动快照）。

## ③ 知识与记忆合流 + 召回质量（09-20）

**解决什么**：把"知识库"和"记忆"合成**一个检索面**——知识页不再只是产出物，而是
与消息、记忆同池竞争的第三层（`kind=page`）。此后召回质量成为主要战场。

**关键实测结论**（都是靠真实查询证伪出来的）：

- **页面融合分与相关性甚至反相关**（相关页 0.21×top vs 噪声页 0.63×top）——
  分数门限必然误杀；结论是**分区间判别**：高分看分数、低分看字面证据
- **"证据"同样不能当门槛**：拼错查询下，语义最相关的页面只有最弱的池内信号，
  而噪声靠全局向量分进来——按证据筛会**同时做错两件事**
- **"没料"时宁可少给**：无关查询从"8 条全是页面"降到 0~2 条；拼错查询靠
  "低分字面兜底席"救回真相关页
- **专名盲区**：`command code` 这类**多词英文专名**此前没有任何通道覆盖——
  12 个相关单元有 11 个连候选池都进不去 → 新增**短语精确匹配通道**

**当前能力**：六路通道融合（向量 / 全文 / 标识符 / 短语 + 页面专属两路）、
页面准入策略、**召回严格度档位**（1~5，默认 3）、结果带层级与来源标注
（`kind` × `origin`）、快照保留份数可配。

## ④ 可观测性：三个事实流（09-21）

**解决什么**：前三个阶段把链路搭起来了，**回查能力却近乎为零**——"这条记忆到底写进去
没有""这次 wiki 为什么跑 / 为什么没跑"只能靠翻库和反推代码。这一天按**视角**把日志拆成
三条互不混用的事实流：

- `logs/mcp.log` —— **协议层**：谁调了什么工具、参数、耗时、成败（服务端唯一分发点自动写）
- `logs/memory.log` —— **数据层**：哪条记忆被写/读、**内容全文**、来自哪条路径
- `logs/wiki.log` —— **流水线层**：编译跑到哪、花了多少、断在哪；新增**触发判定留痕**
  （`trigger_check` 记下 `should_run` / `reasons` / `dirty`）

**关键设计**：写入点在数据层、而"从哪来"只有协议层知道 → 用 contextvar 传来源标记，
不必改一长串函数签名；写入点一律"建目录 + 追加打开"，**手工删掉日志文件甚至整个 `logs/`
也能自动重建续记**（已实测 + 回归覆盖）。

**滚动与归档**：由 `logs` 配置段统一控制（全局默认 + 单文件覆盖，空则回落），滚动规则
**二选一**（按大小**优先** / 按自然日），归档进 `logs/archive/<日志名>/`，默认保留 30 天。
机制本身不是难点，**难在"两条规则互斥 + 优先级明确"**——否则滚动时机不可预测。

**同一天暴露并修复的问题**（Roadmap #1/#2）：驱动这次排查的，恰恰是**新加的
`trigger_check`** —— "某次为什么跑"第一次可查，顺藤查出 wiki 会**静默落后于记忆，
而系统一直显示健康**：三个叠加缺陷（部分失败被打标记 / **manifest 谎报基线** /
L1 全失败仍跑 L2）+ 一个观测盲区（`align` 只看 manifest diff，**61 条输入无任何
页面引用却报"健康"**）+ 一个配置漏配（`wiki.llm` 漏配 timeout → 继承默认 60s，
而 L1 是长调用）。

**方法论收获**：这几个缺陷**没有一个会抛异常、没有一个会让测试变红** —— 它们是
沉默的。能挖出来，靠的是先让系统能回答"当时到底发生了什么"（三个事实流），再拿
时间线去对。可观测性不是运维附属品，它是**把静默失败变成可发现问题**的前提。

## ⑤ 把"跑得住"钉死（09-22）

**解决什么**：④ 让系统**能回答"当时发生了什么"**，这一步才谈得上照证据收口 ——
前一阶段暴露的问题**没有一个会抛异常、没有一个会让测试变红**，全靠时间线对出来。

### 5.1 编译可靠性：从"能跑完"到"失败也不骗人"

| 改动 | 为什么 |
|---|---|
| **分组分批**（`wiki.plan_batch_max`，默认 40） | 分组是"**输出规模随输入线性增长**"的调用，101 条一次性分组会真卡到超时 |
| **组级并发**（`wiki.page_workers`，默认 3） | 各组之间无依赖，串行是纯浪费；实测 **32 组约 48 分钟 → 约 12 分钟** |
| **结果按组序重排** | 完成顺序不确定，直接 append 会让页序随机漂移、**产物不可复现** |
| **429 进程级共享闸门** + 尊重 `Retry-After` | 并发后多个 worker 会同时撞同一 RPM 窗口，**各自独立退避会"共振"**（一起恢复、一起重试、再撞限）；上限 300s 防服务端给离谱值把任务卡死 |
| 限流多给重试（`max_retries+1+2`） | RPM 窗口是分钟级，默认 3 次尝试常常不够 |
| `HTTPException` 纳入瞬态重试 | `IncompleteRead`/`RemoteDisconnected` **继承自 `http.client.HTTPException` 而非 `OSError`** —— 旧捕获漏掉它们，表现为"切网丢一组、一次都不重试" |
| **组级失败剔除新基线** | 与"会话级失败"是**同一个坑、粒度更细**：单组失败不影响整会话（对），但会话仍算成功 → 那几组的记忆照样写进新基线、被永久掩盖。实测 23 组里 3 组失败、**20 条记忆**差点被静默丢弃 |
| **跨进程单飞行锁**（`O_CREAT\|O_EXCL`） | MCP 钩子与手工脚本曾**同时**写同一批产物（日志出现两个"两段式：先分组"，101 vs 102）。`threading.Lock` 只管进程内；`msvcrt.locking` 实测**跨进程无效**；`psutil` 不在依赖里（缺失会退化成"锁永久有效"） |
| **进度逐步落盘** + **计时双口径** | `call_seconds`（累计调用耗时）与墙钟 `seconds` 并列：机器休眠会把墙钟撑大（实测一次 L2 显示 33052 秒 ≈ 9.2 小时而实际约 1 小时），据此曾**误判成"上游重试了 9 小时"** |

**教训**：可观测性的缺口会**反过来制造错误判断** —— 日志静默时，"慢"和"死"看起来一模一样，
排查者会做出破坏性动作（实测因此两次杀掉正在正常工作的编译）。

### 5.2 运维缺口：待更新记忆可以"看"和"删"

`wiki --action pending|ignored|drop|restore`（HTTP 同步四路由）。**边界刻意画死**：
只处理**尚未进 wiki**（`align` 报的 added/changed）的记忆 —— 它们没被任何页面引用，
**删除不产生死链**；已进 wiki 的记忆删除需要墓碑表 + 引用重映射，是另一个量级
（`docs/memory-deletion.md`），`drop()` 会**拒绝**那类 id。

- **软删除**（`wiki_ignore_at` 打时间戳）：记忆仍存在、仍可召回，只是不进 wiki；可 restore。
  且**不触发任何重编** —— 它本来就不在基线里，去掉后 diff 依然是零（09-22 实测验证）
- **硬删除**：蒸馏表行 + units 投影 + 向量，**必须 `confirm`**；删完**重建 manifest**，
  否则 `align` 会把它报成"失去输入"而触发一次毫无意义的重编

按用户决定，**MCP 侧暂不暴露**删除（后续可经接口提供，但需用户确认）。

### 5.3 模型：切到 `xiaomi/mimo-v2.6-flash`

上游新上架、**价格与 V2.5 持平**，按"同价优先新模型"切换；`mimo-v2.5` 留作**同价回退位**。
ID 经项目客户端实测探测确认（`mimo-v2.6` / `mimo-v2.5-flash` 均不被该端点支持）。
**思维链占比与 JSON 遵从性待收尾时与 V2.5 重做一次对比**（外部消息称质量大幅领先）。

### 召回精排（rerank）的实测诊断（2026-09-22）

**先说结论：现在没有"精排"，只有一道纯分数门限。**

```
六路通道融合 → hybrid_search（按分数降序）
  → safe_cutoff_hits：
      页面   —— 不套分数门限（只受 page_max_keep 配额）
      非页面 —— 要求 score ≥ curate_floor × top（默认档 3 = 0.8 × top）
      兜底   —— 非页面至少保 1 条
```

**三个具体问题**（都有实测证据）：

1. **门限锚定在 top 上 —— 噪声当锚点会全盘皆错**
   拼错查询 `windowsctrol`：top1 是**完全无关**的「AgentMemHub 页面召回调优」
   (1.238)，门限因此被抬到 0.990，24 条候选只留 4 条 —— 而其中 3 条是页面
   （不受门限管），非页面只留下了那条噪声本身。
2. **系统性误杀低分真相关**
   同一查询：「**WindowsControl 项目架构与技术栈**」(0.701)、
   「OCR GPU 加速 / window_control」(0.638) 全被切掉。
   查询「Windows 下怎么设置 git 代理」时，**答案本身**「Git 代理与 SSL 配置处理」
   以 **0.789 vs 门限 0.809（只差 0.02）** 被切。
3. **页面与记忆两套待遇（不对称）**
   页面有"字面兜底席"，低分真相关页 **0.195** 也能进结果；
   记忆/消息**没有兜底席**，于是 0.701 的更高分真相关反而被切。

**根因**：六路融合分属于 **RRF 类倒数排名融合**，其**绝对差**不代表相关度差 ——
"乘性相对门限"这个工具本身就选错了：它假设"分数与相关度同尺度"，而这个假设已被
反复证伪（页面层甚至**反相关**：相关页 0.21×top、噪声页 0.63×top）。

**三条路线的实测与决策（2026-09-22）**：

| 路线 | 延迟 | 成本 | 确定性 | 决策 |
|---|---|---|---|---|
| **LLM 精判**（`LLMFinalJudge`） | **+1~3s** | 每次召回一次 LLM 调用（token 费） | **不确定**（同候选可能给不同结果） | **否决** |
| **本地 cross-encoder** | **约 100~300ms** | **0** | **确定**（可复现、可缓存） | 可行，待排期 |
| **规则改进**（对称化 + 门限策略） | **0** | 0 | 确定 | **优先** |

**为什么否决 LLM 精判**（两条，第二条是结构性的）：

1. 用户判断：**成本不可控 + 延迟明显**。Agent 侧或许无感（它本来就在等 LLM），
   但**接口与面板查询能明确感知**。
2. **更硬的一条：缓存救不了它**。rerank 结果缓存的收益取决于**查询重复率**，而
   面板/接口的查询是**人输入的**，重复率天然很低 → 缓存几乎不命中，"每次都发一次
   LLM 请求"无从缓解。**这是结构性缺陷，不是调优能解决的。** 外加 LLM 输出
   **不确定**，会让"召回结果可复现"这条既有原则失效。

**本地 cross-encoder 的实测延迟**（本机纯 CPU，onnxruntime + CPUExecutionProvider；
脚本 `exports/wiki_work/diag_rerank_latency.py`）：

```
单条 query 编码     1.6 ms
单条 passage 编码   70 字 2.1ms / 150 字 4.9ms / 300 字 6.9ms / 600 字 13.1ms
```

cross-encoder 对**每个 (query, doc) 对**都要独立前向（不像 bi-encoder 能复用 doc
编码），所以成本 ≈ 逐条编码 × 参数量倍数：

- **30 候选 × 同规模 reranker ≈ 106 ms**
- **30 候选 × base 级（约 3.3× 参数）≈ 282 ms**

真实候选更长、再加首次模型加载，实际落在 **200~500ms** 量级 —— 且可用"**只精排
top-N**"进一步压缩（候选池 30 条，只精排前 10~15）。**零 API 成本、零 token 费、
结果确定**，与 LLM 的 1~3s + 每次花钱不是一个量级。

**顺带纠正一个直觉**：`LLMFinalJudge`（`agentmemhub/rag/ext.py:52`）**实现是完整的**
（temperature 0、刻意剔除分数防锚定、fail-closed 退 `safe_cutoff`），测试也齐
（`tests/rag/test_rag_ext.py`）—— 但**生产链路零调用**（`rag_bridge.search()` 里没有
任何 `judge=`，只有引擎自带的调试 CLI 用）。**既然 LLM 路线被否，它只能作为
"cross-encoder 之外的另一条腿"留档，不再优先。**

**增量诊断脚本**：`exports/wiki_work/diag_rerank_gap.py`（对比 `curate=False/True`
的差异，列出被门限切掉的条目）。

**更远的方向**（README Roadmap 同源）：更多 Agent 接入（Claude Code / Cursor /
Gemini CLI / CodeBuddy）、记忆折叠压缩（超长会话压缩、相邻轮折叠）、存储扩展
（按 source 分片/归档）。
