## 1. 先回答你提的四个问题

### 1.1 `role` 有什么用？为什么它是个真问题

`role` 是 `units` 表里的**层级维度**，回答"这条单元是什么级别的知识"；它与 `origin`（来源维度：native/external）**正交**。实际取值与含义：

| role | 含义 | 谁写的 |
|---|---|---|
| `user` / `assistant` | 原始对话消息（**碎片**） | 采集适配器 → `rag ingest` |
| `tool` / `reasoning` / `patch` / `shell` / `meta` | 其他事件类型 | 适配器（**不进索引库**，`reasoning` 走开关） |
| `distilled` | 蒸馏记忆 | `distill._project_one` |
| `wiki` | wiki 页面（**整页**，不切片） | `wiki_index.project_pages` |

**它不是一个装饰字段，它实际控制 7 件事**：

1. **准入闸门** —— `DEFAULT_ROLES = ("user", "assistant")` 是白名单（`rag/source.py:15`），
   白名单外的 role **根本不进索引库 → 搜不到**。`tool/patch/meta` 永不入库。
2. **召回分层** —— 页面层 / 记忆层 / 消息层走不同通道与策略。
3. **判重范围** —— `project_memories` 只与 `role='distilled'` 的既有单元比相似度（`distill.py:1655`）。
4. **价值分基线** —— `memstore.py:243` 按 role 给不同初始分（`BASE_VALUE_DISTILLED`）。
5. **健康对账** —— `health.py:55` 用 `role='distilled'` 计数校验投影一致性。
6. **面板统计** —— `web/aggregates.py:115` 按 role 出分布图。
7. **轮次语义** —— 原 `memos.py:135-141`（该文件已随 v2.8 移除 MemOS 一并删除）：只有 `role=='user'` 才**开一个新对话轮**。

**为什么投喂必须关心它**（这就是我问这个问题的原因）：

投喂文档的段落如果直接塞成 `user`：会被当作"用户说的一句话"，**产生虚假对话轮次**，
蒸馏时语义偏移成"用户说了…"，面板会话视图里也会冒出一堆假消息。
若图省事用一个新 role（如 `document`）**却不加进白名单**，则**静默不入库、搜不到**——
这类"配置了没效果"的坑本项目踩过三次（`wiki.single_shot_max` / `wiki.workers` / `wiki.enabled`）。

**但更好的一条路是根本不用消息层**：精炼文档直接进**页面层**（现成的 `role='wiki'`），
绕开 role 白名单与轮次语义问题（详见 §1.3）。

### 1.2 "原件"指什么？两份数据怎么存

你的定义我理解为**两级物料**，这个划分是对的，但有一处我建议改：

| 层 | 内容 | 我建议 |
|---|---|---|
| **原始层** | 网页快照（HTML/MHTML）、PDF/Word 二进制、图片字节 | ✅ 保留，但**只存字节 + 元数据，不进召回面** |
| **可读层** | 转换后的 Markdown / TXT / OCR 文本 | ✅ 进召回面与知识管线 |

**建议改动**：你提到"原始数据类似于碎片化记忆" —— 我建议**不要把原件层当记忆层**。
理由是**召回面只能吃文本**：原件是 PDF 字节/HTML 源码，它没有"记忆"语义，
混进碎片层只会稀释检索质量。**"碎片化记忆"应该是可读层的产物，不是原件本身**。
所以分层是：`原件（字节，只读、不召回）→ 可读文本（进召回面）→ 记忆/页面`。

**存放位置（这是有实测依据的技术决策）**：

现状体量：源库 `agentmemhub.db` **710.8 MB**，索引库 `session_rag.db` **176.4 MB**，
已有快照 **5 份 / 共 0.88 GB**。而**快照 = 索引库整库 + wiki 产物全目录**（`snapshot.py:73-105`），
**源库不在快照内**。

于是三个选项：

| 方案 | 后果 | 判定 |
|---|---|---|
| 放进**索引库** | 每份快照都要复制素材 BLOB。若素材 1 GB → 快照从 ~190 MB 涨到 ~1.2 GB **× keep 份** | ❌ **不可接受** |
| 放进**源库** | 不在快照内（省空间），但源库语义是"采集到的会话"，混入二进制污染定位；且已 710 MB | ⚠️ 勉强 |
| **独立库 `database/materials.db`** | 与快照解耦，可单独定保留策略；正好是你要的"**专门的数据库**" | ✅ **推荐** |

**大文件是否进 BLOB**：SQLite 读 BLOB 要整块载入内存，几 MB 的 PDF 尚可，几十 MB 就难受。
建议**内容寻址的文件系统 + 库里记 hash**：
`raw/<sha256前2位>/<sha256>.<ext>`，库里存 `sha256 / mime / 大小 / 原始 URL / 转换器版本`。
这样**溯源强度不变**（hash 是锚），库不膨胀，且文件可被任何工具直接查看。

**溯源链的完整形态**（这是"任何数据后续都能溯源"的落地）：

```
原件 sha256 ──→ materials 表（元数据 + 可读文本）
                    │
                    ├──→ [精炼档] 文档页 frontmatter `origin: external` + `doc: <material_id>`
                    │              → units(role='wiki', origin='external') → 召回命中
                    └──→ [素材档] 会话 container → units(role='user'/'assistant') → 蒸馏记忆
                                                              → wiki 页面
```
反查路径：召回命中 → `units.wiki_path` → 页面 frontmatter `doc:` → `materials` → 原件 hash。
**当前这条链有两个断点**（§3 详述）：页面层把 `doc:` 的 id 丢了；采集层不写 `origin`。

### 1.3 投喂分几层？精炼文档要不要"二次转换"

**关键在于"转换"这个词其实混了两件事，必须拆开**：

| 动作 | 定义 | 是否必需 |
|---|---|---|
| **格式转换** | 原件字节 → 可读文本（HTML→md、PDF→md、图片→OCR） | **必需，无例外**。连投喂 md 也算"已转换"（直通） |
| **知识加工** | 可读文本 → 碎片 → 蒸馏 → 编译页面 | **分档，不一刀切** |
| **入图** | 套 frontmatter、进页面层、投影进召回面 | **必需**，但**可以纯规则完成、不需要 LLM** |

**所以对你的问题——精炼文档（项目文档、别人的教程文章）要不要二次转换——答案是：**

- **格式转换照做**（它可能就是 HTML，得先变成文本）；
- **跳过碎片化与蒸馏** —— 因为它本身就是"一个主题一页"的形态，拆碎是**反向做功**。
  这不是我的臆断，是项目已有的结论：`wiki_index.py:10-14` 写明
  "L2 页面本身就是 LLM 提炼后的'一个主题一页'——它已经是最优召回粒度。再切回碎片
  等于把整合过的知识拆散（wiki 是切片整合的产物，切回去是反向做功）"；
- **但仍要做一次"入图"** —— 生成带 frontmatter 的**文档页**，投影进 `units(role='wiki')`，
  这样它才可被召回、可被 Obsidian 看到。**这一步用规则就能做，不一定要 LLM。**

**于是两档分工**：

| 档 | 适用素材 | 路径 | 要不要 LLM |
|---|---|---|---|
| **精炼档（浅加工）** | 项目文档、教程、论文、规范的网页/PDF | 转换 → 套 frontmatter → 文档页 → 页面层投影 | **可纯规则**（可选 LLM 做摘要/建链接） |
| **素材档（深加工）** | 散乱笔记、会议记录、聊天导出、多主题长文 | 转换 → 落成"会话" → 碎片 → 蒸馏 → 编译 | 走现有管线（已有 LLM 环节） |

**档位怎么定？我不建议"自动判定精炼度"** —— 上游全仓库查无此类逻辑（见 §2），
且"是否精炼"是主观的，自动判定会不可预测。建议：**投喂时显式声明**
（`depth: page | session`，或由 Agent 判断后显式传），默认值可配。

### 1.4 "Agent 驱动"与 LLM 开关

你要的"C 路线里 Agent 驱动可通过配置选择是否采用 LLM"，我理解为**两个正交的开关**：

1. **谁来驱动流程**（`driver`）：程序化批处理 / Agent 交互式
2. **LLM 参与哪些环节**（`llm`）：转换、摘要、入图建链，各环节独立

设计成配置段（与现有 `rag:` / `wiki:` 平级）：

```yaml
feed:
  driver: program | agent        # 谁发起：程序化 CLI 批处理 / Agent 通过 MCP 交互
  convert:
    llm: false                   # 转换阶段是否让 LLM 参与（PDF 表格/图片理解）
  page:
    llm: false                   # 入图阶段是否让 LLM 写摘要/建交叉引用
  depth_default: page            # 未显式声明时的默认加工档
```

⚠️ **必须警惕的坑**：本项目**三次踩过"假开关"**（配置项没有任何消费点，
而默认值恰好等于硬编码值，所以既不报错也不让测试变红，能潜伏数月）。
所以**每个开关都必须有真实消费点，并进 `scripts/check_config_keys.py` 的可查范围**。
`llm: false` 这一档尤其要有测试覆盖"不装 LLM 也能跑通"。

## 2. 上游调研结论：你想找的方案，它没有

你让我查"那个开源 Skill 有没有类似方案"。**结论是：没有，两块都要自建。**

| 你的问题 | 上游的实际情况 |
|---|---|
| 精炼文档能否直接收录、不二次加工？ | **没有"原样收录"路径。** 唯一浅加工入口是 ingest 场景 C 的第三选项「仅创建摘要页」（`workflows/ingest.md:102`），但它的**触发条件是"计划新建页面 > 5 个"，与素材精炼程度无关**。且即便选了它，产物仍是 **LLM 重写的摘要页**，原文永不进 wiki |
| URL/链接投喂怎么处理？ | **零 URL 能力。** `scripts/` 只有 router.py + lint.py，无任何 http/URL 处理；文档明确要求用户**自己**用 Obsidian Web Clipper 转成 md 放进 `raw/`（`skills/wiki/README.md:264`）。唯一的"发链接自动下载"是**教用户自己写进宿主 memory** 的示例配置，不是 skill 功能 |
| 有没有"按精炼度决定加工深度"？ | **没有。** 全仓库检索"精炼/精华/高质量/官方文档/教程"**无匹配**。决定深度的只有三个启发式：新建页面数 >5、内容矛盾、合并歧义 |
| 数据分几层？ | **真实数据面只有两层**（`raw/` 不可变原件 + `wiki/` 产物）。**不存在碎片/中间记忆层**，且明确"wiki 本身就是记忆"（`query.md:18`） |

**对我们的意义**：
- ①"精炼文档直接收录"**需要我们自己设计判据** —— 上游没有可照搬的逻辑（我们反而有更好的基础：
  页面层整页不切片的机制上游没有）；
- ②**URL 抓取是净新增能力**，上游把这件事划给了外部工具；
- ③ 上游**没有**碎片层，我们有（会话→记忆）。这是我们的复杂度来源，也是我们召回质量更高的原因——
  **投喂不必把上游的两层结构照搬过来**。

**顺手可借的**（细节见 `external-ingest.md` §5）：`query` 回写的两档分流、`.trash` 回收站语义、
lint 的 P0/P1 分档、矛盾标注三件套、"何时问人"的四条判据。
⚠️ 一个实现级提醒：上游 `lint.py:59` 用 `rglob("*.md")` 且**未排除 `.trash`**，
导致回收站里的页面会被算进页面集合并误判为孤岛页 —— 我们若做回收站要显式排除。

## 3. 现状盘点：能复用的 / 必须补的

### 3.1 能直接复用的（下游基本齐全）

| 能力 | 位置 | 状态 |
|---|---|---|
| 页面层整页投影（不切片） | `wiki_index.project_pages` | ✅ 现成 |
| 页面来源判定 | `wiki_index.py:44-45,86-99` 解析 frontmatter `origin: external\|feed` 与 `doc:` | ✅ 有测试（`test_wiki_index.py:178-201`） |
| 召回 `origin` 过滤 | `rag_bridge` / `mcp_server` / `web/app` | ✅ 现成 |
| 蒸馏记忆来源判定 | `distill._project_one:1557` | ✅ 实测 `external` 正确 |
| 会话容器 + 幂等锚 | `Store.replace_source` / `src_id` | ✅ 现成 |
| 快照 / 回滚 | `snapshot.py` | ✅ 现成（但见 §1.2 的坑） |
| 配置继承与审计 | `config.py` 四种继承形态 + `scripts/check_config_keys.py` | ✅ 现成 |

### 3.2 必须补的（地基 + 断点）

**① 采集层不写 `origin`（实测确认）**
`rag/ingest.py:334-336` 的 `INSERT INTO units` 列清单**没有 `origin`**，
所以投喂文档的**原始段落**落库为 `NULL`，召回侧 `or "native"` 兜底 → **被标成"自有沉淀"**。
实测：

```
原始事件落 units → origin=None        ❌
蒸馏投影落 units → origin='external'  ✅
```
**修法**：`run_ingest` 写 units 时按 `source` 映射 origin（与 `_project_one` 同一口径）。
⚠️ 这条**独立于路线选择**，且现在没有 feed 数据，改动风险极低。

**② 页面层把 `doc` id 丢了**
`wiki_index.parse_page` 里 `doc_m` **只用于判定 `is_external`**，
返回的字典里**没有 `doc` 字段**（`wiki_index.py:85-100`），
而投影写 units 的列也只有 `source/conversation_id/seq/role/turn_key/src_id/time/title/text/chars/wiki_path/origin`
（`wiki_index.py:178-185`）—— **`doc` id 没有被持久化**。
后果：召回命中一个投喂页后，**无法从 units 反查到是哪份外部素材**，只能靠 `wiki_path` 去读页面文件、
再从 frontmatter 里抠——页面一旦被重编或删除，溯源就断。
**修法**：`units` 加 `doc_id` 列（沿用现有的幂等 `ALTER TABLE ... ADD COLUMN` 补列模式），投影时写入。

**③ 口径不统一**
`docs/data-architecture.md` 原写 `source=pdf/web`，代码判 `source == "feed"`。
**以 `feed` 为准**（单一来源标识，格式信息放 `meta`/`converter` 字段）。

**④ 直写通路也不带 origin**
`rag_bridge.import_bundle:463-468` 硬编码 `source='memory'`、`role='user'`，且 INSERT 无 `origin`。
若"Agent 驱动投喂"要复用这条直写通路，**同样要改**。

### 3.3 硬约束：投喂页面不能放进 wiki 产物目录 ⛔

`scripts/wiki_aggregate.py:929-963` 的写盘逻辑：

- **全量模式**：先算本轮域目录，然后 `shutil.rmtree` 掉**所有不属于本轮的域目录**（:942-946）；
- **每个域目录**：删掉该域上一轮的全部 `*.md` 与 `*.json`（:959-963）。

注释里写得很清楚，这是**故意的**（"产物是纯派生物，清掉随时可重建"；
不清会导致"227 页的产出目录里躺着 449 个 md"）。

**后果**：任何放进 `out_l2_*/` 的投喂页面，**下一次全量聚合就会被删除**。
所以投喂页面必须有**自己的旁路根目录**（例如 `exports/wiki_work/out_feed/`），
并且 `wiki_index.project_pages` 要支持**多根**：

- 现在 `project_pages(idx, l2_dir, ...)` 只吃**一个根**（`wiki_index.py:133-145`）；
- `src_id = f"wiki_{crc32(rel)}"`、`seq` 也**由相对路径派生**（:83-91），
  多根时**不同根下的同名相对路径会撞**，必须给 `rel` 加根标签；
- 结尾的"全量对齐"清扫（删掉磁盘上已不存在的投影）**必须同时覆盖两根**，否则切换根时会误删。

这是一处**中等改动**，但性质明确、边界清晰（§7 计入阶段 3）。

**✅ 2026-09-25 已加固防护**：清理逻辑原本是"凡是不在本轮 `keep` 里的目录一律 `rmtree`"，
**会把用户放在产物目录里的东西一起删掉** —— 实测把产物目录直接当 Obsidian vault 用时，
`.obsidian/`（编辑器配置）会被静默删除、不可逆。现抽成 `_prune_stale_domain_dirs()`
并加两道闸：**跳过 `.` 开头的隐藏目录** + **只清 `%02d-` 数字前缀的域目录**
（逐字复现旧逻辑验证：目录从 `['.obsidian','01-旧域','02-本轮域','用户自建目录']`
变成只剩 `['02-本轮域']`，连"用户自建目录"都没了）。
**通用教训：产物目录一旦允许用户放东西，清理逻辑就必须白名单化，不能黑名单化。**

### 3.4 附带发现的**生产 bug**：顶层 `index.md` 的链接指向 `.json`

**与投喂无关，但既然查到了就记下来** —— 这是知识库**主入口导航**的缺陷。

实测（`exports/wiki_work/out_l2_mimo/index.md`，422 行）：

```
顶层 index.md  ->  .json 链接 286 条 ; .md 链接 76 条     ❌ 79% 坏链
域级 index.md  ->  .json 链接   0 条 ; .md 链接  1 条     ✅ 正常
```

**根因**：增量路径的 `render_index_from_disk()`（`scripts/wiki_aggregate.py:637,642,652`）
用 `d.glob("*.json")` 收集页面、并把 `jf.name`（即 **`.json` 文件名**）直接拼进链接：

```python
for jf in sorted(d.glob("*.json")):            # :637
    pages.append((d.name, jf.name, ...))       # :642  ← 拿的是 .json 名
L.append("- [%s](%s/%s) — %s" % (title, dname, fname, summary))   # :652
```

而全量路径的 `render_index()` 用 `p["_file"]`（`.md`）是**正确的**（`:602-603`）。
所以**增量更新一跑，正确索引就被坏的覆盖掉** —— 域级 index 走的是另一条路径，因此没被污染。

**影响**：用户/Obsidian 点开顶层索引的条目，看到的是 JSON 原文而不是知识页。
**修法**：`glob("*.md")`（或保留 `.json` 读取元数据但输出时换成 `.md`）＋ 一条测试锁住"index 里的链接必须指向存在的 `.md`"。
**这同时也暴露了**：项目**缺一个针对产物的结构 lint**（断链 / index 与实际文件不一致 —— 正是上游 `lint.py` 的 P0 项之一）。

**✅ 已修（2026-09-24）**：`render_index_from_disk()` 改为**以 `.md` 为准**枚举页面
（`glob("*.md")`，跳过 `index.md`），`json` 仍作 title/summary 的首选来源、
缺失时回落解析 md 自身的 frontmatter 与 `**摘要**：` 行（新增 `_page_meta_from_md()`）。
新增 3 条测试并做了**红→绿验证**（暂存修复时 2 条确实失败）。磁盘上那份坏索引一并重建：

```
修复前： .json 链接 286 条 / .md 链接 76 条
修复后： .json 链接   0 条 / .md 链接 362 条     （行数 422 不变）
```

**四个硬伤（当前不能直接挂进 Obsidian）**：

1. 🔴 **`[[标题]]` 在 Obsidian 里 100% 解析不了**。
   原生 Obsidian 按**文件名 basename 或 frontmatter `aliases`** 解析，**不认 `title`**
   （`title` 要装 Front Matter Title 那类第三方插件才有加成）。
   实测 **L2 948/948 命中 `title`、0 命中文件名；L1 860 处同样 0 命中** →
   **1808 处链接全部显示"未创建"**，点一下会**新建空文件污染目录**。
   修法首选**每页加 `aliases: [<title>]`**（同名即可，零改文件名）——
   这正是上游 skill 强调 `aliases` 的原因（`external-ingest.md` §1.2 已记录），
   **项目文档里早就写下这个坑却一直没落地**。
   ⚠️ **但有前置条件 → 见第 2 条。**

2. 🔴 **19 组重复标题会让 `aliases` 产生歧义**。
   39 个文件共用 19 个标题（例："AgentMemHub 踩坑与根治经验"在 `03-` 与 `05-` 各一页）。
   加 aliases 后 Obsidian 会报 **ambiguous link** → **必须先把标题收敛为全局唯一**
   （或按域加前缀）。这是 `aliases` 方案的**前置条件**，也是我上一版评估漏判的一条。

3. 🔴 **L1 是"一文件多页"，与 Obsidian 的文件级图谱根本不兼容**。
   224 个文件里有 **784 个 `# 标题` 页面**；L1 的 860 处链接中 **222 处指向本文件之外**
   （物理上不存在，`docs/llm-wiki.md:136` 明说"跨会话链接为 0"），638 处虽在本文件内，
   也必须写成 `[[文件名#标题]]`（3 段式）才能解析，而当前是 `[[标题]]`（2 段式）。
   → 两条路：L1 **按页拆成一页一文件**，或**只把 L2 挂进 vault、L1 移出**。
   后者站得住 —— `wiki_index.py:14` 已写明"L2 覆盖了 98.7% 的 L1 内容，
   L1 只是中间态，不进召回面（只作下钻）"。

4. 🔴 **顶层 `index.md` 的 286/362 条链接指向 `.json`** —— 生产 bug（§3.4），
   在 Obsidian 里点开是 JSON 原文，**主入口导航坏掉 79%**。

**另需处理的脏项**：

5. 🟠 **586 个 `.json` 副产物会污染 vault 文件树**。Obsidian 开启
   "Detect all file extensions" 时它们会出现在文件树与快速切换里。
   → **不要把产物目录直接当 vault 根**，应加一个**只导出 `.md` 的 vault 打包步骤**（顺手过滤 manifest）。

**判定**：⚠️ **可行，但比"零代码验证"重得多**（我上一版按 L2 抽样得出"只差一行 aliases"，
**低估了**）。真实落地顺序：

```
修 .json bug → 只把 L2 当 vault（L1 移出）→ 标题全局去重 → 加 aliases
→ 补 tags / ISO date → 加 log.md → 只打包 .md 的 vault 步骤 → 补结构 lint 防漂移
```

**前四步是硬前提**，缺任一个图谱就用不起来。

**顺带确认的两件事**：
- 采集层**主动丢弃附件**（`adapters/sqlite_conversation.py:25` 的 `_SKIP_PART_TYPES` 含 `"attachment"`）
  → 将来投喂图片要另开通道，不能指望现有采集链。
- 项目里**不存在任何 Obsidian/vault 实现**，`obsidian` 关键字命中的**全是文档规划**；
  `export.py` 只导出会话、`scripts/export_memories.py` 只导出记忆，**都产不出 vault**。

## 8. 开工计划

原则：**地基先行 → 先窄后宽 → 每一步都有可验收的产出**，避免"做了一堆但看不到东西"。

### M0 · 地基（0.75 天）
**先做，因为它独立、风险低，而且是所有路线的公共前提。**
- 修 `origin`（采集层）+ `doc_id`（页面层）+ 统一口径
- **顺手修顶层 `index.md` 的 `.json` 坏链**（§3.4，独立 bug、2 小时、立刻见效）
- **验收**：新增测试证明 feed 会话的原始段落 `origin='external'`；
  投喂页投影后 `units.doc_id` 可反查；**index 里的链接全部指向存在的 `.md`**
- ⚠️ 不动任何既有行为（现在没有 feed 数据，等价于加空逻辑）

### M1 · 素材库 + md 直通（1.5–2 天）
- 独立库、内容寻址、CLI 基础；转换器只做 **md/txt 直通**
- **验收**：`agentmemhub feed 某.md --depth page` → 素材入库（原件 + 可读）→ 生成文档页 → **能被召回**
- 🎯 **这是第一个可见价值点**：端到端跑通，证明架构成立

### M2 · 入图两档 + 旁路根（2–2.5 天）
- 旁路根 + 多根投影改造 + 精炼档/素材档分流
- **验收**：① 跑一次**全量 wiki 聚合**后投喂页**仍在**（R1 的锁）；
  ② 素材档投喂能走完"会话→蒸馏→编译"

### M3 · 真实格式（2–3 天）
- HTML → URL 抓取 → PDF → DOCX（按你实际要投喂的格式排优先级）
- **验收**：投喂一个真实网页链接与一个 PDF，端到端可召回、可溯源回原件

### M4 · 入口与人机（1.5–2 天）
- CLI 批处理、MCP 工具（Agent 驱动 + LLM 开关）、面板入口、日志
- **验收**：`feed.convert.llm=false` 与 `true` 两条路都有测试；投喂全程可在日志复盘

### M5 · 收尾（1.25 天）
- `log.md`（知识演进史）+ 文档收口 + 全量回归
- ~~Obsidian vault~~ → 🅿️ **暂缓**（用户决策 09-24）：改造成本高于预期，
  施工图留在 §5.1，将来重启即可
- **验收**：文档与 `AGENTS.md` 同步；测试基线更新并全绿
