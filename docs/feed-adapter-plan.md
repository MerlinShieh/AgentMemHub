## 1. 需求分析：从用户表述拆出五条需求

> 用户原话（2026-10-10）：*"专门做一个【转译层】或者【适配器】，对内提供统一的接口，
> 对外扩展不同投喂数据的适配解析能力。可以针对不同的投喂数据做不同的等级处理……
> 除了最原始的数据，还需要保留下载的源码或者网页镜像，以及最后生成的最终的 md 文档
> （知识库/交付物）。通过适配层处理之后变更为统一的交付物后……和我们的 wiki 记忆做
> 并列关系，两边数据互不影响。然后记忆召回时看是否可以对知识库进行召回。"*

| # | 需求 | 拆解 | 对应设计 |
|---|---|---|---|
| **R1** | **转译层**：对内统一接口、对外可插拔 | 一个 `Converter` 注册表（照 `adapters/` 同构模式），所有格式的输出收敛为**同一份契约**（`FeedDocument`）；新增格式 = 新增一个转换器文件，不动主干 | §3.2 / §3.3 |
| **R2** | **分级处理**：md/txt 一等公民 → 网页链接（含公众号）→ PDF → 图片 OCR | 四级 T1–T4，按此顺序落地；每级有**独立的失败降级策略**，低级失败不阻塞高级 | §7 |
| **R3** | **三段保留**：原始数据 + 下载源码/网页镜像 + 最终 md | `raw/`（不可变原件，内容寻址）→ `mirror/`（中间形态：HTML 源码、渲染快照、OCR 中间产物）→ `out_feed/`（最终 md，知识库本体）；三段由 `materials.db` 一张登记表串成溯源链 | §3.1 / §4 |
| **R4** | **与 wiki 记忆并列，互不影响** | 存储并列（独立目录树）、数据并列（`origin='external'`）、生命周期并列（wiki 全量重跑不动知识库；知识库重投喂不动 wiki）、**编译隔离**（投喂内容不进 L1/L2 编译，自有 wiki 不混入外部内容） | §2 / §5 |
| **R5** | **召回时可以召回知识库** | 最终 md 投影进 `units(role='wiki', origin='external')`，六路召回的页面层通道**天然覆盖**；`memory_search` 的 `origin` 入参现成，可混排可过滤 | §5.3 |

**一条隐含需求（用户没明说但必须做）**：
**R6 幂等与重转** —— 同一文件重复投喂不产生重复数据（内容 hash 锚）；转换器升级后
可以对既有原件**批量重转**（这就是三段保留的价值：原件永远在，md 随时可再生）。

## 2. 关键架构决策：单轨"纯并列"主线

旧计划（09-24）是**双轨**：

- 精炼档（浅加工）：转换 → 文档页 → 页面层投影
- 素材档（深加工）：转换 → 落成"会话" → 碎片 → 蒸馏 → wiki 编译

用户本次的表述——"**并列关系，两边数据互不影响**"——明确了取**单轨**：

> **投喂数据只走"转译 → 统一 md → 知识库页面层"，不进记忆/蒸馏/wiki 编译链路。**

| 对比项 | 旧双轨 | 新单轨（本文） |
|---|---|---|
| 投喂内容会进自有 wiki 页面吗 | 素材档会（蒸馏后参与编译） | **绝不** —— 两边内容零混合 |
| 要动 `role` 白名单/会话容器吗 | 素材档要（旧风险 R4） | **不用动**（风险消除） |
| 要修采集层 `origin` 缺口吗 | 是前置地基 | **降级为顺手修**（feed 不走采集链；但 `import_bundle` 的 origin 参数仍要补，供 Agent 直写外部知识） |
| 散乱长文（会议记录/聊天导出）怎么办 | 蒸馏成多条记忆 | 整页进页面层（页面层**整页不切片**，召回粒度=页，长文可分节多页） |
| 工程量 | 10.5–13 天 | **9.5–10.5 天**（少 2 天，且风险面小得多） |

**代价（要向用户明示）**：投喂内容**不会产生"记忆"**——记忆报表、蒸馏、价值分体系
都看不到它；它只以"知识库页面"的形态存在，在召回时与自有 wiki 页面同台竞争。
如果将来要"投喂的散乱素材也能蒸馏成记忆"，再把旧计划的素材档捡回来（架构上不冲突，
`source='feed'` 的判定代码都还在）。

## 3. 核心概念模型

### 3.1 三段物料（R3 的落地）

```
第 1 段 · 原件（raw）        不可变字节，内容寻址，永不改写
   exports/feed_store/raw/<sha256前2位>/<sha256>.<ext>
   例：公众号文章 → 抓到的 HTML 字节；PDF → PDF 字节；md → 文件原字节

第 2 段 · 镜像（mirror）      转译过程的中间形态，按 doc_id 归档，可重生成
   exports/feed_store/mirror/<doc_id>/
   例：index.html（落地页源码）、rendered.html（若走无头渲染）、
       ocr.json（OCR 中间结果）、images/（下载的文中图片，已解防盗链）

第 3 段 · 交付物（kb）        最终 md = 知识库本体，进召回面
   exports/wiki_work/out_feed/<slug>.md
   带 frontmatter：origin: external / doc: <doc_id> / title / source_url / doc_time
```

**为什么第 3 段放 `wiki_work/out_feed/` 而不是 `feed_store/`**：与 `out_l1_mimo/`、
`out_l2_mimo/` 目录级并列，`project_pages` 多根改造的"根"就是它；将来挂 Obsidian
也是与 L2 平级的一个 vault 子树。全部在 `exports/` 下 ⇒ 已被 gitignore 覆盖。

**溯源链（任何一条召回结果都能回放到原件）**：

```
召回命中 units(role='wiki', origin='external')
   → units.doc_id → materials.db 登记行
   → raw_path(sha256) / mirror_path / kb_path / source_url / converter+version
```

### 3.2 统一交付物契约 `FeedDocument`

转译层对内的**唯一接口**。所有转换器（不管吃的是 md、URL、PDF 还是图片）
都必须产出它；下游（登记、发布、投影）只认它：

```python
@dataclass
class FeedDocument:
    doc_id: str        # 内容锚：sha256(原件字节) 前 16 位
    title: str         # 文档标题（抽取或文件名回落）
    markdown: str      # 最终 md 正文（统一交付物）
    kind: str          # text | url | wechat | pdf | image（转换器认领的类型）
    source_ref: str    # 原始路径或 URL
    doc_time: int      # ⚠️ 文档自身时间（发布/修改），不是投喂时刻
                       #    —— distill._origin_time 的时间语义硬约束，错则时间衰减全错
    mirror: dict       # 镜像文件相对路径表（可空）
    converter: str     # 转换器名 + 版本（重转判据）
    meta: dict         # 格式细节：编码、页数、图片数、抓取耗时…
```

### 3.3 转换器注册表（R1 的落地，照 `adapters/` 同构）

```
agentmemhub/feed/
├── __init__.py        # CONVERTERS 注册表 + get_converter()（照 adapters 模式）
├── base.py            # Converter 协议：can_handle(ref) / convert(ref) -> FeedDocument
│                      #   + version 属性（重转判据）
├── document.py        # FeedDocument 契约 + 校验
├── registry_db.py     # materials.db 读写（登记表 + 状态机）
├── store.py           # 三段目录的读写（内容寻址、镜像归档、kb 发布）
├── converters/
│   ├── text.py        # T1：md/txt 直通（零依赖）
│   ├── url.py         # T2a：普通网页（抓取→正文抽取→md）
│   ├── wechat.py      # T2b：公众号特化（反爬、js_content、图片防盗链）
│   ├── pdf.py         # T3
│   └── image.py       # T4：OCR / 多模态
└── service.py         # 门面：ingest(ref) 全流程编排（认领→登记→转译→发布→投影）
```

**认领规则**：按 `can_handle()` 顺序认领（显式 kind > URL 域名特征 > 扩展名 > 内容嗅探）。
公众号链接（`mp.weixin.qq.com`）由 `wechat.py` 优先于 `url.py` 认领。
**未知类型必须显式报错**，不许静默跳过（旧约束表里"未知 source 被静默跳过"是踩过的坑）。

### 3.4 状态机（materials 表）

```
received ──convert──▶ converted ──publish──▶ published
    │                     │                     │
    └────── failed ◀──────┴────── failed ◀──────┘（retract：kb 撤下但原件保留）
              │
              └─ retry（换转换器版本重转，回到 convert）
```

每次转换记录 `converter`+`version`+耗时+错误；`failed` 不删原件（三段保留的意义）。

## 4. 数据流与存储布局

```
  投喂入口（M1: CLI ／ M5: MCP 工具 ／ 面板随"面板重做"惯例后置）
      │  agentmemhub feed add <路径|URL> [--kind 显式类型] [--dry-run]
      ▼
  ① 认领与查重          converters 注册表认领 kind；
      │                  sha256(原件) 查 materials 表 → 已存在则报"重复投喂"（可 --force 重转）
      ▼
  ② 原件落盘            raw/<hash2>/<sha256>.<ext>（内容寻址，写后校验）
      │                  materials 登记：status=received
      ▼
  ③ 转译                converter.convert() → FeedDocument
      │                  中间产物落 mirror/<doc_id>/；status=converted
      │                  🔘 feed.convert.llm 开关（PDF 表格/图片理解，默认见 §10-Q4）
      ▼
  ④ 发布                套 frontmatter（origin: external / doc: <doc_id> / doc_time…）
      │                  → out_feed/<slug>.md；status=published
      ▼
  ⑤ 投影                wiki_index.project_pages 多根扫描（out_l2_mimo + out_feed）
      │                  → units(role='wiki', origin='external', doc_id, wiki_path)
      ▼
  ⑥ 消费（全现成）       六路召回（页面层通道）· memory_search(origin=…) ·
                         面板来源筛选 [投喂] 标签 · 溯源反查 materials → raw 原件
```

**materials.db 表结构草案**（独立库，**不进快照轮换**——旧计划 §1.2 的决策，快照=索引库+wiki 产物，素材库入快照会 ×keep 份放大）：

```sql
CREATE TABLE materials (
  doc_id      TEXT PRIMARY KEY,      -- sha256 前 16 位
  sha256      TEXT NOT NULL,         -- 原件全 hash（锚）
  kind        TEXT NOT NULL,         -- text|url|wechat|pdf|image
  source_ref  TEXT NOT NULL,         -- 原始路径或 URL
  title       TEXT,
  doc_time    INTEGER,               -- 文档自身时间（epoch 秒）
  raw_path    TEXT NOT NULL,         -- raw/ 相对路径
  mirror_path TEXT,                  -- mirror/<doc_id>/ 相对路径
  kb_path     TEXT,                  -- out_feed/ 相对路径
  converter   TEXT,                  -- 名字@版本（重转判据）
  status      TEXT NOT NULL,         -- received|converted|published|failed|retracted
  error       TEXT,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL
);
CREATE INDEX idx_materials_status ON materials(status);
CREATE INDEX idx_materials_sha ON materials(sha256);
```

## 5. 并列关系与召回接入（R4/R5 的语义澄清）

### 5.1 "并列、互不影响"的四层含义（都要有测试锁）

| 层 | 含义 | 保障机制 |
|---|---|---|
| **存储并列** | `out_feed/` 与 `out_l2_mimo/` 是两棵独立目录树 | `_prune_stale_domain_dirs` 只清 `out_l2_mimo` 内 `%02d-` 前缀目录（白名单防护已在）；**测试锁：跑一次全量 wiki 聚合后，out_feed 一个字节不变** |
| **编译隔离** | 投喂内容**不进** L1/L2 编译输入；自有记忆**不进**知识库页面 | `wiki_compile`/`wiki_aggregate` 的输入是 L1 产物+源库会话，`out_feed` 不在任何输入路径上（结构性隔离，加测试断言 manifest 输入不含 feed） |
| **数据并列** | 同在 `units` 表但 `origin` 维度分开：`external` vs `native` | 投影时写 `origin='external'` + `doc_id`；召回/面板可按 origin 过滤（现成） |
| **生命周期并列** | 删除/重投喂知识库不影响 wiki；wiki 全量重跑不影响知识库 | 删除走 `retract`（撤 kb 页 + 删投影行，原件保留）；wiki 侧对 `out_feed` 只读 |

### 5.2 一个必须直面的细节：`project_pages` 多根改造

现状 `project_pages(idx, l2_dir, …)` 只吃一个根。改多根时三个坑（旧计划 §3.3 已定位）：

1. `src_id = wiki_<crc32(rel)>`、`seq` 由相对路径派生 ⇒ **不同根下同名相对路径会撞**，
   `rel` 必须加根标签（如 `feed::<rel>` / `l2::<rel>`）；
2. 结尾的"全量对齐"清扫（删磁盘已不存在的投影行）**必须覆盖所有根**，
   否则漏扫一根会把那根的投影全删光；
3. 空页面/点目录跳过逻辑对两根一致适用（现成）。

### 5.3 召回接入（R5）

**答案是：可以，而且几乎免费。** 知识库页面投影进 `units(role='wiki')` 后：

- 六路召回的**页面层通道**自动覆盖（它按 role 取数，不分 origin）；
- 融合排序里知识库页面与自有 wiki 页面**同台竞争**（默认混排）；
- `memory_search` 的 `origin` 入参现成：`native`=只搜自有 / `external`=只搜知识库 / 缺省=全部；
- 命中结果带 `[投喂]` 标签（`mcp_server.py:154` 现成）与 `doc_id`（M0 补列后），
  Agent 可据此反查原件。

**默认行为需要拍板**（§10-Q2）：混排（知识库参与竞争）还是默认只搜自有。
我的建议：**混排**——用户投喂的就是想让它在回答里被用上；不想用时 `origin=native` 过滤。

## 7. 解析复杂度重理（用户 10-10 要求：T1 之外的档必须重新理清）

### 7.0 先给"复杂度"下定义：它是四个独立维度，不是一个难度值

"这个格式好不好解析"是错的问法——**任一维度塌陷都会毁掉整档**：

| 维度 | 问的问题 | 塌陷的后果 |
|---|---|---|
| **A 可达性** | 字节拿得到吗？ | 拿不到 ⇒ 这档根本不存在（反爬 / 登录墙 / JS 渲染） |
| **B 结构可提取性** | 正文边界识别得出来吗？ | 提进来一堆导航广告页脚 ⇒ 噪声入库 |
| **C 保真度** | 拿到的是原文的**意思**吗？ | 表格散架、公式消失、图表没了 ⇒ **静默失真**（最危险，因为看起来成功了） |
| **D 可复现性** | 重跑一次结果一样吗？ | 不一致 ⇒ R6"批量重转"的承诺失效 |

**D 维度是本项目此前完全漏掉的，而它直接冲击 R6。** 分析：

- 本地解析器（pypdf / trafilatura）**是确定性的**：同版本 + 同输入 ⇒ 同输出，重转可复现 ✅
- **凡 LLM 参与的环节（表格还原、图表理解、图片 OCR）都是不确定的**：同输入重跑可能给出不同 md ❌

> **由此立一条设计纪律（v2.1 新增）：LLM 只许参与"一次性的语义加工"，其产出必须立刻冻结进 `mirror/`。**
> md 若需重生成，从冻结的中间态**重放**（确定性），而不是重调 LLM。
> 配套：materials 记 `llm_used` 标志；重转时 `llm_used=true` 的记录默认跳过，需 `--force` 才重调。
> 这样 R6 的"换解析器后可批量重转"才真正成立。

**下面逐档拆亚型。关键结论先给：T3 与 T4 都不是"一个转换器"，而是"一个分派器 + 若干亚型转换器"**——
因为同一扩展名下的真实复杂度可能差 10 倍（文字版 PDF vs 扫描版 PDF 完全是两件事）。

#### 7.0.1 脚本还是 LLM？（用户 10-10 追问；本节结论适用于全档）

**先纠正这个二选一的问法**：不是"按格式选脚本或 LLM"，而是"**按流水线的阶段**决定谁来做"。
一条投喂要过五个阶段，每个阶段的答案不同：

| 阶段 | 做什么 | 谁做 | 为什么 |
|---|---|---|---|
| **① 获取** | 发 HTTP、落字节、存镜像 | **脚本（必须）** | LLM 抓取不可复现、超时不可控，代理/重试/反爬都得自己实现；而且"拿到的是什么"本身是**证据**，必须落盘 |
| **② 格式解析** | HTML→DOM、PDF→文本层、DOCX→XML、图片→像素 | **脚本（必须）** | 纯机械转换，脚本更快、更准、更确定 |
| **③ 正文去噪** | 从 DOM 里认出正文，去导航/广告/评论/页脚 | **脚本优先**（readability 类启发式）；**质量信号不达标才升级 LLM** | 启发式对绝大多数常规页面够用且确定性；只有怪异版式才需要语义判断 |
| **④ 结构还原** | 表格→md 表格、公式、图表含义 | **脚本尽力**；表格/公式 LLM 可救援 | 脚本能拿到行列结构；合并单元格/跨页表格/公式需要"理解" |
| **⑤ 语义加工** | 摘要、分类、建交叉引用、起标题 | **LLM**（可选，默认关） | 这才是 LLM 真正不可替代的地方 |

**为什么不能让 LLM 直接吃原件——三个硬理由**：

1. **不可复现（§7.0 的 D 维度）**：同一份 HTML 两次交给模型，输出会变；而"换更好的转换器后
   **批量重转**"要求的恰恰是**同输入同输出**。脚本满足，LLM 不满足。
2. **更贵且更差**：现代网页的标签/属性/内联样式/脚本通常占字节数的 **80~95%**（M3 用真实样本实测确认）。
   把 300 KB HTML 直接喂模型 ≈ 数万 token，而模型还要在噪声里找正文，**准确率反而低于
   "脚本先抽成 3~5 KB 纯文本再交给它"**。
   ⇒ **LLM 不是解析器的替代品，它是解析产物的消费者。**
3. **不可测**：脚本解析能写"给定 fixture HTML → 断言抽出这段文字"的确定性测试；
   LLM 解析只能写飘忽的断言，回归时无法区分"是代码坏了"还是"模型变了"。

**结论：脚本是主干，LLM 是出口（分层兜底，不是二选一）**：

```
① 获取(脚本) → ② 解析(脚本) → ③ 去噪(脚本)
                                  ├─ quality 达标 ────────────→ 直接用（零 LLM 成本）
                                  └─ quality 不达标（R21 静默失真）
                                       └─ feed.convert.llm = true ?
                                            ├─ 是 → LLM 从**已解析的文本**（非原始 HTML）里抽正文
                                            │       → 产出**立刻冻结进 mirror/**（D 纪律）
                                            └─ 否 → failed(needs_llm) + 可操作指引
```

> **一个额外收获**：这条链让 §7.5 的**质量自评从"事后报告"升级为"升级触发器"**——
> 它现在是 LLM 介入的判据，而不只是给人看的指标。两个职责都靠它。

**回到你问的 PDF / Word**：

| 格式 | 脚本能做到什么程度 | 需要 LLM 吗 |
|---|---|---|
| **Word (.docx)** | **几乎不需要** —— `.docx` 本质是 ZIP+XML，有**真实语义结构**（标题层级/段落/表格），`python-docx` 确定性抽取；**难度接近 T1，不属于 PDF 那一类** | ❌ 不需要 |
| PDF **T3a** 文字单栏 | 文本层直接抽，近乎无损 | ❌ 不需要 |
| PDF **T3b** 表格/多栏 | 行列结构能拿；合并单元格/跨页表格会散；**公式拿不回**（结构性上限） | 🔘 可选救援 |
| PDF **T3c** 扫描件 | 拿不到（没有文本层） | ✅ **是**（渲染成图 → 多模态/OCR），LLM 真正有价值的场景 |
| 图片 **T4c** 图表 | 拿不到（OCR 只能取字，取不了"意思"） | ✅ **是**，必须多模态描述 |

⚠️ **一个要避免的旧坑**：旧文档把 DOCX 与 PDF 并列成"二进制类"，但 **DOCX 简单得多**——
有语义结构、纯 Python 可解析、确定性、零成本。M4 里给它的时间应显著少于 PDF，
**不要因为"都是文档格式"就同一对待**。

**Agent 驱动（旧计划路线 B）的正确定位**：
Agent 有 Read 工具、能看 PDF 与图片，价值在 ③④ 阶段（尤其 T4c）。但
**不要把 Agent 当成整条管线**，正确做法是——**让 Agent 成为"其中一个转换器"**：

```bash
# Agent 自己读完原件后，把转好的 markdown 交回同一条管线
agentmemhub feed add --stdin --title "…" --source-ref "<原始URL/路径>" --converter agent
```

登记为 `converter=agent:<model>` + `llm_used=true`，**其余（登记 / 三段保留 / 发布 / 投影 /
召回 / 溯源）全部复用脚本管线**。这样既拿到 Agent 的多模态能力，又不破坏可复现、可批量、可溯源。

**唯一的例外（什么情况下"LLM 直接吃原件"才是对的）**：
③ 阶段脚本彻底失效 **且** ② 阶段也拿不到可用文本（例如整页 canvas 渲染的图表、
排版极复杂的扫描件）。此时把原件（或渲染图）交给多模态模型是**唯一办法**，但必须承认它是
**不可复现的一次性加工**：
- 记录 `llm_used=true` + 具体模型；
- 产出**冻结进 `mirror/`**（不能只留在 kb，否则无法审计）；
- 质量标记为"LLM 一次性产出"，`feed list --low-quality` 可筛出供人工复核。

### 7.1 T1 · 一等公民：md / txt（纯文本直通）

- **零依赖**：读字节 → 编码嗅探（UTF-8/GBK 回落）→ md 直通；txt 包一层最小结构化
  （标题=文件名或首行，正文原样）。
- `doc_time`：frontmatter `date:` > 文件 mtime。
- **它是全链路的验证载体**：M1 用它端到端跑通（登记→raw→kb→投影→召回）。
- **📌 Word (.docx) 归在这里（v2.1 新增）**：`.docx` 是 ZIP+XML，有**真实语义结构**
  （标题层级 / 段落 / 表格），`python-docx` 确定性抽取 ⇒ **与 T1 同级的"脚本直通"，不需要 LLM**。
  它**不属于 PDF 那一类**（详见 §7.0.1 的提醒）。估时归入 M4 但只有 ~2 小时。

### 7.2 T2 · 网页（按**【可达性】**分四亚型——A 维度是这一档的主矛盾）

网页的复杂度**几乎全在"能不能拿到正文"，而不在"怎么转 md"**。三亚型的难度不是一个量级：

| 亚型 | 特征 | 复杂度 | 依赖 | 估时 | 本版处置 |
|---|---|---|---|---|---|
| **T2a 静态页** | 正文就在首次 HTTP 响应里 | B 中（正文抽取） | httpx + trafilatura 或 bs4+lxml | 1 天 | ✅ 做 |
| **T2b 公众号** | `mp.weixin.qq.com`，DOM 极规整 | A 中（反爬）+ B **低**（结构固定） | 同 T2a + 特化抽取 | +0.5 天 | ✅ 做（你的高频场景） |
| **T2c JS 渲染页** | 正文靠 JS 执行后注入（SPA/瀑布流） | **A 极高**：需无头浏览器（Playwright + Chromium ≈ 400MB） | Playwright（**可选依赖**） | 一次性环境成本 + 0.5 天 | 🔶 **v2.2 改判：做，但作为"二级兜底"**（见下方 §7.2.1）——参考实现证明它一举解决反爬与渲染两件事 |
| **T2d 登录墙/付费墙** | 需账号会话 | A 极高（法律与凭据风险） | — | 不可估 | ⛔ **明确不做**：失败 + 指引手工导出 |

> **一个反直觉的结论**：T2b **比** T2a **更好做**。公众号文章 DOM 结构几十年不变
> （正文恒在 `#js_content`），抽取规则是确定性的；它唯一的难点是**访问**（反爬）。
> 而 T2a 面对任意站点，正文抽取是启发式的、质量方差大。所以"公众号要特殊处理"是对的，
> 但特殊在**抓取层**，不在解析层。

**T2a 要点**：
- 抓取：`httpx`（走系统代理 `HTTP_PROXY=127.0.0.1:7897`，项目既有惯例）；
  **响应原始 HTML 字节落 `raw/`，落地页源码落 `mirror/`**（用户点名的"下载的源码或网页镜像"）；
- 正文抽取选型：`trafilatura`（质量最好）vs `bs4+lxml` 手工规则（lxml 环境已有）。
  **M3 开工时用 3 个真实网页对比定**（§10-R1）；
- `doc_time`：`<meta article:published_time>` > HTTP `Last-Modified` > 抓取时刻；
- 文中图片：下载到 `mirror/<doc_id>/images/`，md 改写为本地相对路径（否则防盗链裂图）。

**T2b 要点（公众号，独立转换器 `wechat.py`）**：

| 问题 | 对策 |
|---|---|
| 非微信 UA 返回"环境异常"验证页 | 伪装微信内置浏览器 UA；**检测到验证页不硬闯**，转兜底通路 |
| APP 分享出的临时链接带 `chksm/token`，可能过期 | 同时存"规范链接"（去参 `/s/<biz_id>`）；过期报 `failed(link_expired)` 并提示重取 |
| 正文在 `#js_content`，通用抽取器可能不认 | 特化抽取：`#js_content` + `#activity-name` 标题 + `publish_time` 脚本变量 |
| 图片 `mmbiz.qpic.cn` 有 referer 防盗链 + `data-src` 懒加载 | 下载带 referer；md 改写为 mirror 本地路径 |
| **兜底通路（一等公民，非补丁）** | ① 浏览器"另存为 HTML" 后 `feed add <文件>`（走本地文件路径）② `feed add --stdin` 粘贴正文。**反爬是军备竞赛，兜底保证功能不死**（风险 R16） |

#### 7.2.1 三级取回策略（v2.2 修正，依据：参考实现 `second-brain-skill` user-guide:540）

> **修正原因**：我原先判"T2c JS 渲染不做"，理由是"装无头浏览器 +2~3 天且不可收敛"。
> 但参考实现（`docs/user-guide.md:540`）用一句话给出了更好的答案：
> **"用户发来微信公众号链接 → 自动 playwright pdf 下载 + 自动 ingest"**——
> 它用**一个工具同时解决了反爬与 JS 渲染两件事**（真浏览器天然通过指纹检测，且 JS 必然执行）。

**修正后的三级策略（成本递增，逐级兜底）**：

| 级 | 手段 | 覆盖 | 成本 | 可复现性 |
|---|---|---|---|---|
| **①** | **脚本直抓**（httpx，代理） | 静态页 / 公众号多数情况 | 零 | ✅ 确定 |
| **②** | **Playwright 渲染**（真浏览器）→ 取渲染后 DOM / `innerText` | 反爬页 / SPA / 依赖 JS 的正文 | 一次性装 Chromium ~400MB；每页慢几秒 | ✅ **仍确定**（同理：DOM 是确定的，只是取回方式变了） |
| **③** | **人工兜底**：浏览器另存 HTML → `feed add <文件>`；或 `feed add --stdin` 粘贴正文 | ②也失败的（登录墙/极端反爬） | 人工 | ✅ 本地文件确定 |

**⚠️ 关键差异：我们不要像它那样导出 PDF 当产物。**
它导出 PDF 是可以的——因为它的知识由 LLM 独占写、从不从 raw 重derive。
但**我们的产物必须是 markdown**（要投影进召回面的文本层、要可 grep、要可重转）。
所以 Playwright 对我们的价值是**"拿到渲染后的 DOM"**，不是"导出 PDF"。
> 唯一保留"导出 PDF/截图"的场景：整页是 **canvas 绘制**、DOM 里根本没有文本
> —— 那时它等价于一张图，归 **T4c** 走多模态，而不是当文本源。

**检测与降级判据（客观，可测）**：
```
抓到的 HTML：抽取正文长度 / HTML 总长度 < 3%  且  命中 SPA 标记
   （__NEXT_DATA__ / id="app" / 大量 <script> 而文本稀少）
        ├─ feed.fetch.renderer = playwright → ② 渲染后重试抽取
        └─ = none（默认）→ failed(js_rendered) + 提示"安装 Playwright 可自动处理此类页面"
```

**开关**：`feed.fetch.renderer: none | playwright`，**默认 `none`**（不强制装 400MB 浏览器）。
理由与 Q4 一致：默认零依赖可跑通，能力按需开启。

**⚠️ 要在 §8.0 的纪律下验证**：Playwright 渲染出来的内容**同样要落 `mirror/`**
（渲染后的 HTML/DOM），否则二级兜底就破坏了"回到原件"的溯源链。

### 7.3 T3 · PDF（按**【内容形态】**分四亚型——这是"PDF 不是一种东西"的地方）

同一份 `.pdf` 后缀，可能是纯文本、可能是扫描图片、可能是加密的，**复杂度差 10 倍以上**。
所以 `pdf.py` 的职责是**先探再派**（probe → route），而不是硬解：

| 亚型 | 客观判据 | 复杂度 | 依赖 | 估时 | 产出质量 |
|---|---|---|---|---|---|
| **T3a 文字版·单栏** | 每页文本 ≥ 50 字符；`find_tables()` 空 | **低**（C 高） | pypdf | 0.5 天 | ✅ 好，近乎无损 |
| **T3b 文字版·含表格/多栏/公式** | 每页文本 ≥ 50 字符；表格命中 | **高**（C 低） | pdfplumber（表格） | +1 天 | ⚠️ 表格可救、**公式基本丢失**、多栏可能串行 |
| **T3c 扫描件（图片型）** | 每页文本 < 50 字符（或全空） | **极高**：等于逐页做 T4 | 渲染（**pypdfium2**）+ T4 通路 | +（T4 的时间） | ⚠️ 取决于 OCR |
| **T3d 加密/DRM** | `is_encrypted` | 不可行 | — | — | ⛔ 要求密码，否则 `failed(encrypted)` |

**路由判据实现（可测）**：
```python
pages_text = [len(p.extract_text() or "") for p in doc]
if doc.is_encrypted: return route("T3d")
if sum(pages_text) / len(pages_text) < 50: return route("T3c")   # 扫描件 → 逐页渲染 → T4
if any(p.find_tables()): return route("T3b")
return route("T3a")
```
- `doc_time`：PDF 元数据 `CreationDate` > 文件 mtime；
- **T3b 的诚实说明**：公式（MathML/LaTeX）在 PDF 里本来就是**排版符号而非语义**，
  任何解析器都拿不回来——这是 C 维度的**结构性上限**，不是实现水平问题。
  若这类文档重要，只能靠 LLM 视觉理解（走 T4 思路，逐页渲染成图），成本另计。

### 7.4 T4 · 图片（按**【内容语义】**分三亚型——OCR 与"理解"是两种能力）

**这是最容易误判的一档**：以为"图片 = OCR"，但 OCR 只能取字，**取不了"意思"**。
一张折线图用 OCR 只会得到坐标轴标签和噪声字符。

| 亚型 | 内容 | 该用什么 | 复杂度 | 估时 | 质量 |
|---|---|---|---|---|---|
| **T4a 文字截图** | 干净的 UI/文档文字，正向 | **本地 OCR 就够**（Windows.Media.Ocr / PaddleOCR） | 低 | 0.5 天 | ✅ 好（中文一般~好） |
| **T4b 拍摄的文档** | 有透视/光照/手写 | 预处理（去斜、二值化）+ OCR | 中 | +0.5 天 | ⚠️ 中低 |
| **T4c 图表/信息图** | 折线/柱状/流程图/思维导图 | **本地 OCR 无效**，必须**多模态 LLM 描述** | 高（且不确定） | +（LLM 环节） | ⚠️ 依赖模型，且**不可复现**（§7.0 的 D 维度） |

**处置策略（因为无法事先区分 T4a 与 T4c）**：
```
先跑本地 OCR（免费、离线、确定性）
  ├─ 文本密度高且非乱码 → T4a 完成，写入 md
  └─ 文本稀疏/乱码 → 说明"图里有 OCR 取不到的东西"
        ├─ feed.convert.llm=true → 升级多模态 LLM 描述（T4c），
        │     结果**立即冻结进 mirror/**（遵守 §7.0 的 D 纪律）
        └─ =false → status=failed(needs_llm) + 指引："这张图疑似图表，
              请开启 --llm 或手工补充说明"
```
**开关**：`feed.convert.ocr: local | llm | off`（默认 `local`；与 Q4 的 `feed.convert.llm` 配合——
`llm` 档才允许升级到多模态）。`off` = 只登记原件不转译。

**沙箱熔断纪律**（本项目 10-08 刚立）：T4c 的 LLM 多模态客户端**必须**走
`AGENTMEMHUB_TEST_SANDBOX` 熔断（照 `wiki_aggregate.make_client` 模式），
测试注入假客户端，**绝不允许测试真调付费接口**（这是踩过 900 秒超时的坑）。

### 7.5 跨档统一：质量自评 + 降级路由（比"注意质量"更实在的机制）

旧文档把"转换质量不可控"列为风险却没有机制。v2.1 补上——**每个转换器都必须交回质量信号**：

```python
FeedDocument.quality: float          # 0~1，本转换的质量自评
FeedDocument.warnings: list[str]     # 人可读的具体问题（不达标原因）
```

| 档 | 质量信号（客观可算） |
|---|---|
| T1 | 恒 1.0（无损直通） |
| T2 | 正文字符数 / HTML 字符数；未本地化外链图片数；命中 SPA/验证页标记 |
| T3 | 平均每页文本字符数；`find_tables()` 命中数；扫描页占比 |
| T4 | OCR 返回文本密度；可疑字符（乱码）占比；是否升级到 LLM |

**落地规则**：
1. `quality < FEED_QUALITY_WARN(默认 0.5)` ⇒ 仍发布（不阻塞），但 `status` 标记 +
   `feed list --low-quality` 可筛 ⇒ **人工可复核**；
2. `warnings` 非空必进 `logs/feed.log` 与 CLI 输出（**不静默**）；
3. 每次失败/降级都写 `materials.status=failed` + `error` 结构化原因，**原件永不删**（可重转）；
4. 降级方向**单向向下**：T4 失败 → 人工文本；T3c → T4；T2c/T2b → T1 本地文件兜底。

> **✅ AGPL 问题已结案（2026-10-14，M4 落地时）**：原计划里"扫描件渲染"只有两个选项 ——
> `PyMuPDF`（**AGPL-3.0，有传染性**）或 `pdftoppm`（poppler，GPL，但作为外部可执行程序

> 所以 `PyMuPDF` **不再需要**，`pdftoppm` 也不必。这条从 §10-R2 的"待定"转为"已决"。
> 许可结论**不是查网页得来的**，而是从**已装包的 metadata**
> （`License-Expression` / `Classifier`）读出来核实的 —— 依赖的真实许可只在装好的那一个版本上确定。

- **依赖与 R2 结案**：`pypdf`(BSD-3) 进主依赖；`pdfplumber`(MIT) + `pypdfium2`
  (**BSD-3-Clause / Apache-2.0**) 进可选档 `feed-pdf`。**渲染不用 PyMuPDF**（AGPL-3.0 有
  传染性），也不用 `pdftoppm`（Windows 上要额外分发可执行程序）。许可全部从**已装包的
  metadata** 读出来核实（`License-Expression` / `Classifier`），不是查网页。
- **T4 图片（OCR）刻意未开工**：T3c 只做到"渲染进 `mirror/` + 报 `needs_ocr`"。
  用户本轮指定的是"PDF 和 docX"；OCR 通路还牵涉多模态客户端与沙箱熔断，单独立项更安全。

**M4 实施中发现的 6 件事（都不在原计划里）**：

① **加密档不能先碰 `len(reader.pages)`** —— 未解密访问会抛 `FileNotDecryptedError`，
   加密档就变成 `crash` 而不是可处置的 T3d。夹具把这条顺序约束逼了出来（有守护测试）；
② **元数据不可盲信** —— 真实 PDF 的 `/Title` 停在 `…[v2022.12`，正文首行才是完整的
   `…[v2022.12.20]`。修法的两个条件都不能省，且**不能用"谁更长"**：截断的元数据标题
   因为多了 `C2A … (Commercial Use)` 反而更长，按长度判就会被它蒙过去；
③ **PDF 日期里的 `Z` 被丢掉 ⇒ `doc_time` 偏 8 小时** —— 时间不是装饰，召回侧的时间衰减按它算；
④ **表格区域必须从正文里剔除** —— `pdfplumber.extract_text()` 里**含**表格文字，
   不剔除同一批字会以"流式正文 + 表格"出现两次（一种"看起来成功"的失真）；
⑤ **合并单元格检测不能用 `id(cell._tc)`** —— lxml 的元素代理**不保证身份唯一**，
   普通 3×3 表格被误判成"有合并"、质量分 1.0→0.8。**假告警比漏报更伤**（会让人不再信任质量信号）；
⑥ **`.docx` 必须按 `w:body` 子节点顺序遍历** —— `document.paragraphs` 与 `document.tables`
   是两个独立列表，分别遍历会让表格全挤到文末（夹具里"表格前后的段落"就是这个坑的哨兵）。

**顺带修的两处既有缺陷**（都是新测试逼出来的，不是 M4 新代码引入的）：

· `ingest()` 返回值的 `kind` **从不回填转换器判定的类型** —— 本地文件恒为空串，而库里存的是
  `pdf`/`docx`：同一件事两个答案；
· `feed lint` 对失败素材**完全不吭声** —— `needs_ocr` 这类"能力缺口"会静默躺在库里。
  现在按 **能力缺口 P1（`awaiting_ocr`）/ 数据损坏 P0** 分开报（混在一起会让"体检红了"失去指向性）。

**第二轮真机验收（2026-10-15，用户提供的真实文档）** —— 又抓出 3 处，其中一处**丢数据**：

用户给了同一份求职文档的 `.docx` 与 `.pdf`（153 KB / 325 KB），一验就出事：

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① | **一行代码从知识库永久消失**（`page.get_by_role("button", name="Submit")`，连"语"字都被吞掉） | 那行等宽字体代码被 pdfplumber 误检成"1 行 2 列"表格，实现照单全收 ⇒ 把它当表格**从正文剔除**，而它又不足以构成表格 ⇒ **两头落空** | 表格判据加"≥2 行且 ≥2 列"；剔除前做**字符覆盖校验**（**同源**比较），不过就放弃剔除 |
| ② | 标题是**半句话**（`…今年有六年有余的工作经`） | PDF 文本层里的"一行"是排版产物，`验。` 落在第二行 | 首行缝合（`titles.join_wrapped`）：只在"下一行明显短于首行"时缝；中文不补空格、英文补 |
| ③ | DOCX 标题成了 **WPS 默认文件名「文字文稿1」** | 那份文档完全没用标题样式、core title 也为空 ⇒ 落到文件名兜底 | 标题多一档**正文首段**兜底；默认文件名判为 junk；限长/占位都记 warning |

顺带修一处**文案自相矛盾**：`low_quality` 的语义是"质量分低 **或** 有告警"，控制台却打成
「质量偏低（1.00）」—— 两者必须分开说（把"分数低"和"有告警"混为一谈会让人不再看这个提示）。

修后复验：PDF `T3a · 质量 1.00 · 1,582 字`（那一行完整保住）、DOCX `1,657 字 · 质量 1.00 ·
标题=正文首段`；两份都进真实库、`feed lint` **P0=0**。
**真机发现的坑已固化成夹具**（`pdf_false_table.pdf` / `pdf_wrapped.pdf`）——
不固化的教训下次改代码还会踩回去。另外标题判据抽成了单点 `feed/titles.py`
（PDF/DOCX 原本各写了一份，必然漂移）。

**第三轮：目录级批量验收（2026-10-15，`D:\TCL\文档`，1811 个文件 / 2.63 GB）**

用户指定"先把**常用文档**这块处理干净"（图片/OCR 优先级放后）。先做认领探测：
**1811 个文件里只有 15 个能进**（pdf 7 / docx 4 / txt 4），大头是 PNG 截图（1324 个）
与工具产物。批量复验又抓出四件事：

| # | 问题 | 命中 | 修法 |
|---|---|---|---|
| ① | **合并单元格让内容重复**：整行合并的标题在 markdown 里被复制 3 遍 | **3/4 的 docx**（接口测试报告是常态，不是边缘情况） | `row.cells` 会重复返回同一格 ⇒ 改按 XML 还原：`w:gridSpan>1` 补空列、`w:vMerge` 续格留空（**留空比重复正确**） |
| ② | **本地 `.html` 一个都进不来**：M3 文档里承诺的兜底通路根本没实现 | 61 个 | `UrlConverter.can_handle` 原先只认 `http(s)://` ⇒ 加扩展名/字节认领；图片按**文件系统**解析、时间取 mtime、`kind=html` |
| ③ | **相对路径图片从未被本地化**：`_HTML_IMG_RE` 硬编码 `https?://` | M3 起就埋着 | 正则放宽到任意 `src`，由下游决定"按 URL 取"还是"按文件读"（公众号恰好全用绝对 URL 才没暴露） |
| ④ | **空壳页面拿满分**：60 份测试报告静态可见文本只有 136 字（全是字段标签），数据是 `<script>` 里 27 KB 的 `var resultData` | 60 个 | 新增 `feed/embeddata.py`：先**把数据取回来**（解析内嵌 JSON → 表格），取不回才打标（质量 0.4 + 指引）。**覆盖率 ≠ 信息量** |

④ 的处置细节值得一提：质量自评按"抽取覆盖率"算，给空壳打了 **1.00** ——
指标算得没错，只是它回答的问题不是"这页有没有内容"。这不靠调权重解决，
而要加一条**形态判据**（`looks_like_label_shell`：以冒号结尾的短行占比 ≥ 30%）。
实测 **51/61 救回**（最高从 424 字 → 18,523 字），9 个救不回的是"结果为空"的报告。

批量复验（76 个可处理文件）：**76/76 成功**、全库 **376,169 字**、
质量 0.90+ 占 65 个；剩余 9 个低质是**真的没内容**（空结果报告 + 模板文件），
已按设计打标并给指引。

**第四轮：5 种"重要文档"适配完成（2026-10-15，用户指定范围）**

用户明确：**图片/OCR 优先级放后**，先把 **md / docx / PDF / pptx / xmind** 这五种
重要文档做好；并强调**未筛选的测试数据禁止写入召回**（本轮全部在隔离目录验收）。

前三种已有，本轮补齐后两种：

| 格式 | 实现 | 实测 |
|---|---|---|
| **PPTX** | `python-pptx` 读分页 + 版面；`## 第 N 页`；**备注一定取**（讲稿比正文更有信息量）；表格走统一渲染；图片落 `mirror/` | 4 份全部成功（最大 130 MB / 36 页） |
| **XMIND** | **零依赖**（ZIP + JSON/XML）；层级 → 嵌套列表；备注/标签压成行内；单画布不加小节 | 14 份全部成功，最大 **20 画布 / 2861 主题 / 94,173 字** |

实施中的四个判断（都值得记）：

① **XMIND 解析顺序不能反**：新版用 `content.json`、旧版用 `content.xml`，
   而那 14 份**两个都有**、`content.xml` **全是同一份 4,309 字节的空壳**
   ⇒ 先读 xml 会得到"看起来成功、实际空"的导图；
② **PPTX 的"图片读取失败"是假告警**：对每个无文字形状都试 `shape.image`，
   线条/自选/空文本框会抛异常 ⇒ 8 页 PPT 报"8 张图失败"（实际 4 张）。
   先判 `MSO_SHAPE_TYPE.PICTURE`。**同一条道理第二次出现**（第一次是合并单元格的
   `id(cell._tc)`）：**假告警比漏报更伤**；
③ **判"PPT 基本是图"要用占比不能用绝对页数**：单页 PPT 必然只有 1 页有文字，
   拿"≤1 页"去判会把正常的一页 PPT 判成"正文都在图片里"；
④ **默认名要成批收进 junk 名单**：`PowerPoint 演示文稿`（PPT 默认 core title）、
   `中心主题`（XMind 默认根名）、`思维导图`（XMind 默认画布名）——
   它们"对所有同类文档都一样"，作为标题等于零信息。这张名单现在是**三个真实素材**
   凑出来的（`文字文稿1` / `PowerPoint 演示文稿` / `中心主题`）。

**第五轮：批量投喂接口 + HTTP 服务（2026-10-15，用户明确提出）**

用户原话要点：**批量投喂**、**以文件后缀控制输入（大小写不强制）**、
**后续可调整哪些格式支持投喂**、**要区分二进制 / path / url 三种输入**、
**这些接口要支持 HTTP 服务**、**后面通过数据看板直接控制**。

| 层 | 交付 | 位置 |
|---|---|---|
| 统一入口 | `ingest_any(source, value, filename, …)` —— 三种形态走同一个门 | `feed/service.py` |
| 批量 | `scan_targets()`（**只读**列清单）+ `ingest_batch()`（逐条、互不中断） | `feed/service.py` |
| 格式白名单 | 后缀驱动、大小写不敏感、**默认跟随注册表**、支持运行时覆盖 | `feed/formats.py`（新） |
| CLI | `feed formats` / `feed scan` / `feed batch [--apply]` | `cli.py` |
| HTTP | `/api/feed/*` 共 11 个接口（含 multipart 直传与长任务批量） | `web/app.py` |

四个设计决定：

① **白名单默认跟随转换器注册表**（而不是写死一份清单）：两处清单必然漂移，
   而"明明支持却投不进来"是最难查的那类问题。加一个转换器就自动支持；
   ⚠️ 但后缀常量必须是**类属性** —— 早先各转换器写成模块级 `EXTS`，注册表收集不到，
   白名单静默退化成"什么都不许投"（第一次跑就撞上）；
② **无后缀放行**：URL（`https://…/s/xxx`）与工具导出的无扩展名报告没有后缀可查，
   硬拦会把它们全挡在门外 ⇒ 交给认领机制按内容判型，判不出来照旧显式报错；
③ **`batch` 默认不落盘**（只扫描列清单，`--apply` 才写）：批量影响面大，
   而"投进去容易、清干净难"。这与用户的"先筛选再落库"是同一条纪律；
④ **运行时覆盖与 yaml 分开**（`logs/feed_formats.json`）：看板要能直接点选，
   但**不该反过来去改用户的 yaml**（与 `wiki_triggers` 的 overrides 同机制）。

两个实测坑：
· **`UploadFile` 必须写在模块顶层**：`app.py` 启用了 `from __future__ import annotations`，
  FastAPI 从**模块全局命名空间**解析路由函数的类型注解 —— 写在 `create_app()` 里的
  import 解析不到，报 `PydanticUserError: …ForwardRef('UploadFile')… is not fully defined`
  （正是该文件第 25 行那条警告说的情形，我还是踩了）；
· **测试隔离多一道**：格式覆盖是**真实路径**（`logs/`）⇒ conftest 用进程级环境变量
  `AGENTMEMHUB_FEED_FORMATS_STATE` 兜死（本项目第四次"测试经真实路径改真实状态"）。

## 11. 参考实现深读：`second-brain-skill`（2026-10-10；上游最新 `0a06755`，2026-04-15）

> 快照在 `exports/wiki_work/refs/second-brain-skill`（不进版本库）；
> `git ls-remote` 已确认远端 HEAD 与本地相同 ⇒ **无更新，分析对当前版本有效**（约 6 个月无维护）。

### 11.0 核心结论：它**不实现**解析——把解析全部外包给宿主 Agent

| 环节 | 它怎么做 | 依赖 |
|---|---|---|
| 素材获取 | **人**（Obsidian Web Clipper 一键裁剪存 `raw/`）或 **Agent**（Playwright 打开链接导出 PDF 存 `raw/`） | 宿主能力 |
| 格式解析 | **Agent 的 Read 工具**（PDF/图片走视觉理解） | 宿主能力 |
| 正文去噪 | **Agent 自己的判断**（全仓库无任何抽取库） | 宿主能力 |
| 内容加工 | Agent 按 `workflows/ingest.md` 的提示词写页面 | — |
| **结构验证** | **`scripts/lint.py`（唯一的实质代码，352 行，零 LLM）** | `PyYAML`（**全仓库唯一依赖**） |

**全仓库依赖只有 `PyYAML>=6.0`**（仅用于解析 frontmatter）。没有 pypdf / bs4 / trafilatura / requests / playwright。
这个数字很有说服力：**在"Skill 形态"下解析是免费的——因为 Agent 本来就带多模态 Read。**

### 11.1 为什么它能这么省，而我们不行（形态差异，不是水平差异）

| 维度 | second-brain-skill | AgentMemHub | 后果 |
|---|---|---|---|
| 形态 | **Skill**（给 Agent 的提示词 + 约定） | **Service**（MCP / CLI / HTTP + 三层数据 + 面板） | Skill 里 Agent 永远在环；Service 必须能独立跑批 |
| 知识产物 | **LLM 独占写，永不从 `raw/` 重 derive** | 编译产物**可再生**（L1/L2 可重跑） | 它**不需要**可复现；我们需要（§7.0 D 维度） |
| 数据面 | **纯文件，无数据库** | 源库 / 索引库 / 产物 三层 | 我们要逐单元溯源（`units.doc_id`） |
| 可批量 | ❌ 一次一素材、对话驱动 | ✅ 批量投喂、断点续跑 | 它的做法在批量场景不成立 |
| 去噪失败 | Agent 自己会看出来并重试（**人/模型在环**） | **无人在环** ⇒ 必须机制化（§7.5 质量自评） | — |

**⇒ 它的"省"有前提。把它的做法直接搬来，会在「批量 / 可复现 / 可溯源」三处崩掉。**
但这恰恰印证了我们 §7.0.1 的结论：**它跳过的是 ②③ 阶段（靠模型免费代劳），
而我们在 ②③ 必须用脚本——因为我们要的是可复现的产物，它要的是"读到就行"。**

### 11.2 它带来的一条**改判**：Playwright 兜底（已并入 §7.2.1）

见 §7.2.1。要点：它用 Playwright 同时解决**反爬 + JS 渲染**，比我原先"伪装 UA + 人工导出"的方案可靠；
但**我们不要导出 PDF**（产物必须是 markdown），只要它渲染后的 DOM。

### 11.3 第二个收获：脚本的**第三种角色**——确定性验证器

我此前把脚本的职责归纳为"解析 + 抽取"（§7.0.1 的 ①②③）。`lint.py` 展示了第三种：
**在产出之后做确定性体检**。这条我们直接可用，而且**正缺**——旧计划 R15 就写了"缺产物结构 lint"，
**正因如此 `.json` 坏链那个 bug 才能存活至今**。

它 7 项检查与我们的对应：

| `lint.py` 检查 | 级别 | 我们的现状 |
|---|---|---|
| 断链 `[[x]]` 指向不存在页 | P0 | ⚠️ 有 `obsidian.verify()`，但**依赖 Obsidian 外部程序**（重、且索引会过期） |
| `[[raw/...]]` 误用（应普通链接） | P0 | 🆕 我们的等价物是**跨根链接**（`out_feed` ↔ `out_l2`）与 `.json` 链接（已修） |
| frontmatter 完整性 | P0 | 🆕 可加：`origin` / `doc` / `title` / `doc_time` 必填 |
| **`index.md` 与实际文件一致** | P0 | 🆕 **我们恰好踩过这个 bug**（286 条 `.json` 链接）——纯脚本几分钟就能全查 |
| 双向链接缺失 | P1 | 🆕 没有 |
| 孤岛页 | P1 | 🆕 没有 |
| entity/concept 缺 `sources` | P1 | 🆕 等价：页面缺 `doc` 溯源字段 |

**建议**：M2 顺带做 `feed lint`（或扩展 `wiki --action lint`）。
**低成本高回报**：它正是防住多根投影/跨根链接出问题的手段，且**纯脚本**（零 LLM、零外部依赖）。
另外照抄它的**非零退出码**（P0 时 `sys.exit(1)`）——可直接当提交门槛与 CI 触点。

### 11.4 一个它自己踩的坑：回收站与扫描器的相互作用（我们要避开）

`wipe.md` 规定"删除 = 移入 `wiki/.trash/`（按原目录结构）"，但 `lint.py:59` 用
`WIKI_DIR.rglob("*.md")` **没有排除 `.trash`** ⇒ 同时产生**两个方向**的错：

1. **误报**：回收站页面被当成正常页面统计入站链接 ⇒ 孤岛页误报；
2. **漏报（更严重）**：回收站页面仍在 `all_ids` 里 ⇒ **指向"已删除页面"的链接被判为有效**，
   真正的断链被静默掩盖——**你永远不会知道有页面已经没了**。

**对我们的意义**：知识库的 `retract`（撤下 kb 页）必须让**所有扫描器显式排除已撤下内容**，
并且要意识到失效是**双向**的。**列入 M2 测试锁**：
"retract 之后，指向它的链接必须被报为断链，而不是静默有效"。

### 11.5 借 / 不借（更新 `external-ingest.md` §5）

**新增值得借**：

| 机制 | 为什么 |
|---|---|
| **Playwright 渲染兜底** | 一个工具同时拿下反爬与 JS 渲染，比"伪装 UA + 人工兜底"可靠（§11.2） |
| **确定性 lint 的 P0/P1 分级 + 非零退出码** | 可直接当提交门槛；我们正缺这一整类检查（§11.3） |
| **`conventions.md`（每库操作偏好，每次操作先读）** | 知识库级偏好文件——我们的 feed 可类比为"每库投喂约定" |
| **多库注册表 `registries.json`**（id/name/root/wiki/raw/lang） | 我们目前单库不需要，但字段设计可参考 |

**新增不该借**：

- **导出 PDF 当投喂产物** —— 丢文本可检索性；我们的产物必须是 markdown（§7.2.1 末）
- **把解析完全交给 Read 工具** —— 破坏可复现与可批量，且我们的产物要进召回的文本层
- **`rglob` 不排 `.trash`** —— 见 §11.4，是明确的反例

### 11.6 它验证了我们的两个判断

1. **"精炼文档跳过二次加工"是对的**：它的 ingest 产出**永远是 LLM 重写的摘要页**，
   原文永不进 wiki ⇒ 它压根没有"原样收录"。我们的"浅加工档（格式转换 + 套 frontmatter，
   跳过蒸馏）"是它没有的能力，值得做（`external-ingest-plan.md` §2 的结论仍然成立）。
2. **"URL 抓取是净新增"**：它把这件事划给了外部工具（Web Clipper）与宿主（Playwright），
   skill 本体零 URL 能力 ⇒ 我们自建抓取层是对的，且现在有了更好的实现参考（§7.2.1）。
