# LLM Wiki：把碎片记忆编译成可读知识库

> 状态：第一级已完成并验证；第二级（跨会话聚合）实现完成，首轮全量验证中。
> 相关脚本：`scripts/wiki_compile.py`（第一级）、`scripts/wiki_aggregate.py`（第二级）。

## 复现步骤（从零到一套 wiki）

### 顺序不能颠倒：前置条件是**蒸馏记忆**

这套流程的输入是 `distilled_memories`（蒸馏产物），**不是原始对话**。
所以必须先把前两步跑完：

```bash
uv run python -m agentmemhub sync      # 采集各 Agent 的对话历史
uv run python -m agentmemhub distill   # 蒸馏成结构化记忆
```

**没有蒸馏数据，wiki 编译就没有输入**——`wiki_compile.py --list` 会列出 0 个候选会话。

### 三步命令

```bash
# ① 第一级：逐会话编译（碎片 → 会话内页面）
uv run python scripts/wiki_compile.py --all --out DIR_L1 --workers 8

# ② 第二级：跨会话聚合（会话内页面 → 主题实体页）
uv run python scripts/wiki_aggregate.py --src DIR_L1 --out DIR_L2 --stage all

# ③ 链接修复（**必须做**，原因见「第二级的死链」一节）
uv run python scripts/wiki_linkfix.py --dir DIR_L2
```

**索引库不用手动传**：三个脚本缺省都会回退到 `agentmemhub.yaml` 里配置的
索引库（第一级 `--index-db`、第二级 `--db`）。只有想用副本、完全不碰生产库时
才显式传路径 —— 本次实测就是这么做的。

**全程只读**：脚本都以 `mode=ro` 打开索引库，产出是独立 markdown 文件，
**不写任何数据表、不改引擎状态**。随时可以删掉产物重跑。

### 先自检环境

```bash
uv run pytest tests/test_wiki_scripts.py -q     # 15 项：不调 LLM、不需要凭据
```

这组测试只覆盖纯函数与产物解析（slug 生成、页面切分、编号提升、链接解析），
任何人在干净环境 clone 下来就能跑，用来确认流程本身可用。

### 成本与耗时参考

以本次全量实测（874 页 → 31 域 → 259 页）为基准：

| 阶段 | 调用次数 | 耗时 | 估算花费 |
|---|---|---|---|
| 第一级（217 会话） | — | ~12 分钟（8 并发） | ¥4–10（取决于是否关推理） |
| 第二级 · 归域 | 10 | 8 分钟 | ¥0.9 |
| 第二级 · 细分 + 编译 | 246 | 39 分钟 | ¥8.4 |
| 链接修复 | 0 | 数秒 | 0 |

**关推理是第一大成本杠杆**：`thinking: disabled`（DeepSeek 官方）把思维链直接归零；
`reasoning_effort: low` **挡不住**——实测思维链仍占输出 69%（编译）/ 94%（归域）。
第二级如果走只能调强度的 provider，这部分开销绕不开。

## 定位

AgentMemHub 原本只有 RAG：查询时从两万条原始碎片里检索，**每次重新推导、无累积**，
优化的是「能不能捞到」。LLM Wiki 是**互补**的第二条路径——把已经沉淀的结论
**编译**成结构化、互相链接、人和 Agent 都能直接读的 markdown 页面，优化的是
「有没有结构」。

两层的数据关系是**单向**的：

```
原始碎片（units / distilled_memories）  ← 真相源，永不被 wiki 改写
        │
        │  编译（只读，单向）
        ▼
    wiki 页面（markdown）  ← 派生物，可随时全量重建
```

RAG 与用户数据可以影响 wiki；**wiki 不会反向影响 RAG**。

## 两级结构

```
1496 条蒸馏记忆
      │
      ├─ 第一级（已完成）逐会话编译
      │     把碎片整理成"会话内页面" —— 871 页
      │     压缩比仅 1.67:1
      │
      └─ 第二级（本次）跨会话聚合
            把同一主题散在多个会话里的页面合并成"实体页" —— 目标 200–400 页
```

**为什么必须两级**：输出长度有硬上限。实测把 45 条记忆一次性编译时，
prompt 15150 tokens、思维链 21483 tokens，输出到 32K 上限仍被截断
（`finish_reason=length`，JSON 未闭合）。必须 map-reduce。

**为什么第一级不白做**：第一级按**会话**切（确定性边界），第二级按**主题**合。
第一级的产出是第二级的输入——它已经是有结构的、带溯源的页面，
比直接喂原始碎片省一个数量级的 token。

## 第一级：会话内编译

### 实测数据（2026-09-18）

| 项 | 值 |
|---|---|
| 输入 | 224 个会话 / 1496 条蒸馏记忆 |
| 产出 | 217 份 md / **874 页** |
| 失败 | 7 个会话（2 空内容 + 5 JSON 截断），可断点续跑 |
| 耗时 | 约 12 分钟（8 并发） |
| 成本 | 约 ¥10（当时的配置，未关推理） |

### 关键约束（都是实测踩出来的）

1. **推理模型的思维链计入 `max_tokens`**。`deepseek-flash` 这类模型
   `reasoning_tokens` 占输出的 63–68%；设 8000 时正文一个字都轮不到，
   直接报"模型返回空内容"。**必须两段式 map-reduce**。
2. **没有现成的分组键**。`topic` 几乎唯一（1543 条 → 1541 个，LLM 给每条单独起名）、
   `slice_key` 是 `*merge*`/`whole`（会话级而非主题级）、`tags` 只有 Agent 主动写的才有。
   → **必须让 LLM 分组**。
3. **`config.py` 的字段白名单会静默吞掉新字段**。写了 `thinking` 却读不到，
   排查半天才发现是白名单没加。现抽为 `_LLM_SCALAR_KEYS` 常量。
4. **控制台编码能吃掉产物**。用量报告里的 `¥` 在 GBK 控制台抛
   `UnicodeEncodeError`，而该 print 在 `write_text` **之前**——跑完 4 页却没落盘。
   已在脚本入口统一 `reconfigure(encoding="utf-8")`。

### 产出的两个固有缺陷（第二级负责修）

- **正文 `[n]` 是会话内序号，`**来源**：[m123]` 是全局记忆 id**。两者同源但
  markdown 只渲染了后者，读者拿到文档**无法自行追溯**。
- **`[[相关]]` 死链率 15.5%**（233/1508）。LLM 引用的是**实体名**而不是已生成的
  页面标题（如引用 `AgentMemHub`，而实际标题是「AgentMemHub 数据库概览与表清单」）。
  跨会话链接为 **0**——第一级每次只看一个会话，物理上不可能引用别的会话的页。

## 第二级：跨会话聚合

### 三个阶段

```
① domains  871 个标题 → M 个主题域
             两段式：先只归纳域表（输出短），再分批把页面归到域表（每批 200）
② plan     逐域把域内页面细分成"最终页"（域内页数 ≤ min_pages 时跳过）
③ compile  逐最终页把源页面正文**重新编译**成一页（真·蒸馏，不是拼接）
```

阶段① 拆成两段是**必需的**：一次调用处理 871 个标题并要求当场分组，
在默认 60s 超时下必然失败；拆开后每次调用要么"输入大输出小"、
要么"输入小输出小"，稳定得多。

### 编号体系：把 `[n]` 提升为 `[m<id>]`

第二级输入前做一次**编号提升**：把每个源页面正文里的会话内序号 `[5]`
替换成全局记忆 id `[m3572]`。这样：

- 聚合后编号**不会冲突**（多个会话的 `[1]` 不会撞车）
- 正文引用**直接可追溯**回 `distilled_memories`
- 顺带修好第一级"只有裸 id 无法追溯"的缺陷

**映射必须查数据库，不能只靠产物**：第一级写进 json 的 `sources` 数组
**没列全**正文实际用到的编号（实测 250/5552 处），只靠产物会留下无法追溯的引用。
权威来源是按 `(source, conversation_id)` + `ORDER BY created_at, id` 重算的
会话内序号——与第一级的 `src_map` 逐字一致。补全后未映射引用从 **250 降到 1**。

> ⚠️ 第一级产出的页面**不能用 `\n# ` 切分**：正文代码块里的 `# 注释` 会被误判成
> 页面边界，实测 47/217 个文件因此错位（最大差 5 页）。可靠特征是
> **`# 标题` 后紧跟 `*type: xxx*` 行**。

### 输入预算保护

一个域里可能有十几个页面被并成一页。单个最终页的源正文总量上限
`MAX_GROUP_CHARS = 60000` 字符，超出按序截断并在页面顶部标注。

### 实测结果（2026-09-18）

| 阶段 | 输入 | 产出 | 耗时 |
|---|---|---|---|
| 归域 | 874 个标题 | **31 个主题域**（覆盖 874/874） | 478s |
| 细分 | 874 页 | **259 个最终页** | 与编译合计 |
| 编译 | 259 个最终页 | 259 页 | 合计 **2366s** |

- **压缩比 874 → 259 = 3.4:1**（第一级只有 1.67:1）
- 平均每页合并 **3.3** 个源页面，最多 **24** 个，单源页 47 个
- 调用 **246 次**，输入 2.02M / 输出 1.05M tokens（其中思维链 69%），估算 ¥8.42

**溯源与链接核验**：

| 指标 | 第一级 | 第二级（修链接后） |
|---|---|---|
| `[m<id>]` 命中率 | 100% | **100%**（8249 处 / 1491 个 id） |
| `[[标题]]` 死链 | 15.5% | **0%** |
| 孤儿页 | 19.7% | 34.7% |
| 跨会话 / 跨域链接 | **0 处** | **887 处** |

> ⚠️ **第二级的死链一度高达 92.6%，这是聚合的必然结果，不是模型写得差**：
> 正文里引用的**第一级标题**在合并后已经不存在了。好在 json 的 `from_titles`
> 记下了每个最终页合并了哪些源页，按这张表重定向后 832/864 处自动修好。
> **第二级必须配 `wiki_linkfix.py` 收尾**，否则链接几乎全废。

**关于孤儿页**：剩下的 34.7% 没有正文入链，但**都能从 `index.md` 和域索引进入**，
所以导航上并不孤立；要降低这个比例需要另外生成"同域相关页"链接，属后续优化。

## 配置：两级刻意不级联

> **选哪个模型**：主力推荐 `xiaomi/mimo-v2.6-flash`（2026-09-22 上游上架，价格与
> V2.5 持平；**质量指标待重测**，同族上一版 V2.5 的实测见选型文档），
> 批量/多次重跑可用免费的 `meituan/LongCat-2.0:free`——完整对比与定价见
> [`docs/model-selection.md`](model-selection.md)。

```yaml
llm:                    # 顶层：provider / 密钥 / 请求头
  endpoint: ...

wiki:
  llm:                  # 第一级（继承顶层，只覆盖差异）
    thinking: "disabled"
  l2:
    llm:                # 第二级（**同样继承顶层**，不继承 wiki.llm）
      reasoning_effort: "low"
      timeout: 900
```

`wiki.l2.llm` 的继承链是 **顶层 `llm` → `wiki.l2.llm`**，刻意**跳过 `wiki.llm`**。
级联继承会让第一级换 provider 时连带改掉第二级——实测踩过：第一级切到
DeepSeek 官方关推理后，第二级因此丢掉了 Command Code 的凭据。

## 失败兜底与格式修复

长任务必然遇到预期外错误（上游 520、超时、空内容、截断的 JSON、余额不足、
并发限流）。`fail-open` 只保证"不中断整批"，**不解决"事后怎么办"**。为此有
两层机制：

### 一、失败清单（`agentmemhub/failures.py`）

每次失败落一条 JSONL（`<产出目录>/failures.jsonl`），跨次运行累积；跑完打印
**按原因分类**的汇总，并把错误归成七类：

| 类别 | 含义 | 应对 |
|---|---|---|
| `quota` | 余额 / 额度不足 | **重试无意义**，汇总里醒目提示去充值 |
| `auth` | 401 / 403 / 鉴权失败 | **重试无意义**，检查 api_key |
| `model` | 模型名不存在 / 不支持 | **重试无意义**，核对 `/provider/v1/models` |
| `rate` | 429 / 并发限流 | 可重试（降低并发更有效） |
| `transient` | 超时 / 网络 / 5xx | 可重试 |
| `format` | 空内容 / JSON 解析失败 | 可重试，或交给修复模型 |
| `unknown` | 识别不出（**不猜**） | 人工看 |

**单独重跑失败项**（不必全量重来）：

```bash
uv run python scripts/wiki_compile.py --all --out DIR --retry-failed
uv run python scripts/wiki_aggregate.py --src DIR_L1 --out DIR_L2 --retry-failed
```

重跑成功后会把该目标的历史失败标记为已解决，汇总里不再出现。

### 二、格式修复模型（`repair_model`）

主模型**返回了内容但 JSON 解析失败**时，把这份**原始输出**交给一个 JSON
遵从性更好的模型转成规范 JSON——而不是丢弃或退化成拼接。

```yaml
llm:
  model: "xiaomi/mimo-v2.6-flash"              # 便宜的主模型（同价优先新模型）
  repair_model: "deepseek/deepseek-v4.1-flash" # 只在失败时出手
```

**几个关键事实**（都是实测的）：

- **` ```json ` 围栏 `extract_json` 本来就能剥**。真正修不好的是**输出被截断**
  （围栏 + 内容未闭合）——修复模型能从已有部分恢复出完整对象。
- **修复只在失败时触发**，占比低（实测 5–10%），一次修复的输入才几 K token，
  成本可忽略。
- **修复失败不改变语义**：修不好照样抛错，绝不假装成功（有测试守着）。
- **不给修复器无限套娃**：修复调用内部直接用 `_post` + `extract_json`。
- **修复提示词禁止编造内容** —— 修复只该转格式，自己造内容会污染知识库。

### 服务接口（补跑不该只能靠人敲脚本）

补跑能力**不能只存在于脚本参数里** —— 那样面板、定时任务、其它程序化调用方
都够不到。所以有一层服务接口（`agentmemhub/wiki.py`），**CLI 与面板走同一份实现**：

```bash
# 查：有哪些未解决的失败、分几类、要不要人工介入
uv run python -m agentmemhub wiki --action failures --out DIR

# 做：只重跑失败项（--stage 留空 = 按依赖顺序补跑两级）
uv run python -m agentmemhub wiki --action retry --out DIR --stage l2 --src DIR_L1
```

**HTTP 接口**（长任务走后台任务，返回 `job` 可轮询进度）：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/wiki/failures?out=DIR[&stage=l1]` | 失败清单摘要（结构化，含 `needs_manual`） |
| `POST` | `/api/wiki/retry?out=DIR[&stage=&src=][&workers=]` | 提交定向补跑任务 |

**Python**：

```python
from agentmemhub import wiki
wiki.failures_summary(out_dir)            # → dict，可直接 JSON 序列化
wiki.retry_targets(out_dir, "l1")         # → ["qwen/xxx", ...]
wiki.retry_failed(stage="l2", out_dir=..., src=..., on_progress=print)
wiki.retry_all(out_dir=..., src=...)      # 按依赖顺序补跑两级
```

**`needs_manual=True`** 表示存在 `quota`/`auth`/`model` 这类**重试无意义**的错误 ——
调用方应当直接提示用户去处理，而不是继续补跑。

## 运行日志（`logs/wiki.log`）

编译是长任务（第二级实测 39 分钟 / 246 次 LLM 调用），**控制台输出一关就没了**。
所以每一步都落盘到 `logs/wiki.log`（JSONL，只追加）：

| 事件 | 何时写 | 关键字段 |
|---|---|---|
| `run_start` | 每次运行开始 | 脚本、阶段、输入/输出目录、并发、参数 |
| `call` | **每次 LLM 调用** | 阶段 tag、成功/失败、第几次重试、耗时、**本次 token 增量** |
| `session_done` / `session_fail` | 第一级每个会话 | source、cid、记忆数、页数、耗时 |
| `domain_planned` | 第二级每个域细分完成 | 域名、最终页数 |
| `page_done` / `page_fail` | 第二级每个最终页 | 域名、标题、合并了几个源页 |
| `run_end` | 运行结束 | 汇总页数、耗时、累计用量 |

**它要回答的四个问题**：

```bash
tail -5 logs/wiki.log                              # ① 跑到哪了
grep '"session_fail"' logs/wiki.log                # ② 哪些会话失败了
grep '"ok": false'    logs/wiki.log                # ② 哪些 LLM 调用失败了
grep '"run_end"'      logs/wiki.log | tail -1      # ③ 花了多少
grep '"session_done"' logs/wiki.log | tail -1      # ④ 上次断在哪
```

程序侧也有查询入口：`agentmemhub.logs.read_wiki_audit(limit=N)`，
传目录则读该目录下的 `wiki.log`（便于测试）。

**日志是旁路**：写失败一律静默 —— 审计绝不能反过来让编译失败，这条有测试守着。

## 成本控制

### 实测：`reasoning_effort: low` 挡不住思维链

第二级归域（150 页，Command Code + `reasoning_effort: low`）：

| 指标 | 值 |
|---|---|
| 调用次数 | 3（含 1 次空内容重试） |
| 输入 tokens | 11,963 |
| 输出 tokens | 25,367 |
| **其中思维链** | **23,777（占输出 94%）** |
| 耗时 | 108s |

**低推理强度 ≠ 低推理量**。`reasoning_effort` 约束的是"允许想多久"的上限，
不改变模型本身的推理倾向——重推理模型在 low 档下依然把 94% 的输出花在思维链上。

**能真正关掉推理的只有 `thinking: disabled`**（DeepSeek 官方支持），
它把 `reasoning_tokens` 直接归零（第一级实测：输出 −62%、耗时 −62%、花费 −52%）。
第二级如果走 Command Code，这部分开销绕不开。

> ⚠️ 脚本打印的"估算花费 ¥"是按 **DeepSeek 价目**折算的参考值
> （`estimate_cost` 的默认参数），走 Command Code 套餐额度时**不代表实际扣费**。

- **用量/成本上报**：`agentmemhub/llm.py` 的 `usage_snapshot()` / `estimate_cost()`，
  脚本收尾打印调用次数、输入输出 token、思维链占比与估算花费。
- **空闲时段半价**：DeepSeek 高峰为周一至周五 09:00–12:00 / 14:00–18:00。

## 链接修复（`scripts/wiki_linkfix.py`）

第一级产出实测（`--dry-run`）：

| 指标 | 值 |
|---|---|
| `[[标题]]` 引用 | 1508 处 |
| 原本有效 | 1272 |
| 规范化后可自动修复 | 11 |
| **无法确定（去链）** | **225（14.9%）** |

**策略刻意保守——只做"能唯一确定目标"的修复**：精确命中 → 保留；
去标点/空白/大小写后唯一命中 → 替换；一方包含另一方且唯一命中 → 替换；
**其余保留文字、去掉链接标记**。

**为什么不去猜**：`AgentMemHub` 这类名字对应二十多个标题，强行指向其中某个
会把读者引到不相关的地方——**比留一个死链更糟**。去链后的名字会进报告，
它们其实是"应该成页但还没有"的清单，正好是补页的输入。

> ⚠️ 修复必须放在**标题定稿之后**：第二级会重写页面标题，先修第一级的链接
> 会全部作废。所以顺序只能是「第二级聚合 → 链接修复 → 索引」。

## 对齐审计与编译清单：wiki 知不知道自己过时了

wiki 是一次性离线编译的产物，RAG 库是活的。此前两边**没有任何同步概念**：
页面只有 `compiled_at` 时间戳，不知道自己"基于哪些记忆的哪些版本"建成。
实测教训：编译完成后真实库发生了三类变更（overlong 截断改写 681 条输入、
qwen 会话删除 -327、投影修复恢复 163 条输入），wiki 全部无感知 ——
163 条有效记忆至今没进 wiki，纯靠"被删的记忆恰好没被引用"才没出死链事故。

### 编译清单（manifest）

两级编译收尾自动写 `manifest_l1.json` / `manifest_l2.json`（产出目录下），
内容是**编译时的输入快照**：记忆 id → 内容指纹（现算 md5）+ 会话归属；
L2 另附 域 → L1 源文件/记忆 的映射。

指纹刻意**不用**库里的 `content_hash` 字段：它只在蒸馏写入时生成，绕过蒸馏
链路的直接改库（overlong 修复 UPDATE 了 content，hash 没重算）会让它失真漏报。

### 对齐审计（只读）

```bash
# CLI
uv run python -m agentmemhub wiki --action align --out <产出目录> [--stage l1|l2] [--db <索引库>]

# HTTP（面板/程序化调用）
GET /api/wiki/align?out=<产出目录>&stage=l2&db=<索引库，可省>
```

回答四个问题：

| 问题 | 指标 |
|---|---|
| 页面引用还有效吗 | `invalid_refs`：库中已删（missing）/ 已转 merged（not_input） |
| 当前输入被覆盖了多少 | `coverage.ratio`（被至少一个页面引用的输入占比） |
| 编译后库变了什么 | `stages.l2.added/changed/removed` + 脏会话清单（有 manifest 时） |
| 要不要重编 | `needs_recompile` |

实测（对齐审计首跑，manifest 以副本库为锚、diff 对真实库）：
新增 163 / 内容变更 681 / 失去输入 26（真删 16 + 状态迁移 10），
脏会话 188 个 —— 与人工考古的数字完全吻合。

### 增量更新（已实现）

align 现在能回答"差多少"，`update` 则直接动手（**不全量重来**）：

```bash
# CLI：只重编脏会话的 L1 页 + 受影响的 L2 域
uv run python -m agentmemhub wiki --action update --l1 <第一级产出目录> --l2 <第二级产出目录>

# HTTP（长任务，后台执行）
POST /api/wiki/update?l1=<第一级>&l2=<第二级>
```

链路（会话为脏单位）：

```
align 定位脏会话 → L1 整页重编（会话隔离，无副作用）
  → manifest_l2 的 域→L1文件 映射定位脏域 → 只重编脏域（partial 模式）
  → 新 L1 文件归入现有域（一次便宜的归类调用，不重跑全量归域）
  → linkfix（L2 标题可能变）→ 索引刷新 → 两级 manifest 刷新成新基线
```

几个关键设计：

- **partial 模式绝不清域目录**：全量模式会清掉"不属于本轮"的目录防止新旧混叠，
  增量模式本轮只编少数域，其它域产物都在磁盘上——清了等于删库。顶层索引
  从磁盘（各域 index.md + 页 json）重建。
- **单成员页沿用源页**：域内细分若某最终页只有一个来源页，直接沿用不再调
  LLM（与全量一致的成本优化）。
- **`_domains.json` 成员按最新页序重写**：L1 页数变化会让旧 members 序号漂移，
  不修正的话下次全量跑会按错误成员聚合。
- **成本**：一次会话蒸馏几条新记忆 → 重编 1 个 L1 页 + 1~2 个 L2 页，
  与全量 20 分钟 / ¥7 不是一个量级。

**触发策略（攒批，已实现）**：更新不跟随每次编译——检测便宜（align 毫秒级只读）、
编译昂贵（LLM）。**检测挂在两个写入入口上**（无后台定时任务）：

- **MCP `memory_save`**：每成功写入一条记忆，异步过一次检测（daemon 线程，
  不阻塞 MCP 响应）；
- **蒸馏收尾**：批量蒸馏落库后同样过一次检测。

前置修复：MCP 直写的记忆此前**不进 `distilled_memories`**（只有引擎与消息层
投影有）——记忆报表看不见、wiki 编译输入完全不可见。现已在 `memory_save`
成功后同步落蒸馏表（`distill.save_direct_memory`：脱敏兜底 + 指纹幂等 +
归档复活，source='mcp' / conversation_id='direct' / slice_key='mcp:<trace_id>'），
units 向量投影由下次蒸馏统一补齐。

三条规则（命中任一且有脏数据即触发，**互不干扰、各自独立判定**）：

| 规则 | 默认 | 语义 |
|---|---|---|
| `schedule` | `["09:00","12:00","18:00"]` | **时点档**而非时钟触发：当天第一次发生在某档位之后的写入，补触发该档 |
| `dirty_memories` | `10` | 脏记忆（新增+变更）达到阈值触发一次 |
| `first_write_daily` | `true` | 每自然日第一次蒸馏写入后触发 |

标记语义：**update 成功才打标记**（时点档/每日首次记录在 `logs/wiki_trigger_state.json`）；
失败不记，下次写入自然重试。update 会把 manifest 刷新成新基线，align 归零，
天然防止重复编译。单飞行锁保证两个触发点撞上时后到者跳过。

规则编辑（运行时覆盖，优先级最高，不改 yaml）：

```bash
# CLI：查看配置与状态
uv run python -m agentmemhub wiki --action triggers
# CLI：手动执行一次检测（--force 绕过规则强制更新）
uv run python -m agentmemhub wiki --action trigger [--force]

# HTTP
GET /api/wiki/triggers          # 查看
PUT /api/wiki/triggers          # 编辑 {"schedule": [...], "dirty_memories": N, ...}
POST /api/wiki/trigger/run?force=   # 手动触发
```

配置位置：`wiki.out_l1` / `wiki.out_l2`（产出目录正式配置位）与
`wiki.update`（规则默认值，yaml 可改）——见 `config.DEFAULT_WIKI`。

**后续路线**：~~把 wiki 页作为**第三路召回源**~~ —— **已完成**（2026-09-20）：
L2 页面整页投影为 `wiki_<crc32>` 单元，走**页面专属的两条通道**（子集向量 +
子集全文）参与六路融合，另有页面准入策略；权威描述见
[`data-architecture.md` §4](data-architecture.md)。知识库与记忆本质是同一种数据，
这与 second-brain-skill、Karpathy wiki 两个参考项目的理念一致。

### 静默失败：manifest 必须只记「实际编译成了什么」（2026-09-21 实测）

这一天发现 wiki 会**静默落后于记忆，而系统一直显示健康**。把排查引出来的，正是
新加的 `trigger_check` 日志（此前"某次为什么跑"只能靠 `fired` 记录反推），顺藤
查出**三个叠加缺陷 + 一个观测盲区 + 一个配置漏配**：

**① 部分失败被当成成功。** `update()` 正常返回、但 `l1.failed = 1` —— 触发器
只 `except` 异常、**从不看返回值**，照样 `_mark_fired`：当日 `09:00/12:00/18:00`
三个档位与 `last_update_at` 被一起消耗，失败会话要等**明天**首次写入才有机会
重试。这与 docstring 写的"失败不记、下次写入自然重试"正好相反。
→ 现在 `failed > 0` 即不打标记，并落 `trigger_fired_skipped` 审计。

**② manifest 谎报基线（最严重）。** `update()` 失败后仍执行最后一步
`build_manifest()`，而它快照的是**「库里现在有什么」**、而不是**「实际编译成功了
什么」** —— 失败会话被写进新基线，此后 `align` 一律报 `✓ 库未变化`，这批脏数据
**永久掩盖**。实测：修正前 manifest 声称 1781 条输入全部已编译，而 L1 页面
`mcp__direct.md` 内容停在两天前。
→ `build_manifest(drop_sessions=…)` 把失败会话剔除出新基线（1781 → 1680），
它下次仍显示为 added —— **这是重试的唯一线索**。

**③ L1 全失败仍跑 L2。** L2 拿磁盘上的**旧 L1** 重跑同样的域，实测白烧
1290 秒 / 42 万 prompt token，产出还只是"同义不同措辞"。
→ 全失败直接跳过 L2。

**④ 观测盲区：align 从不看页面覆盖。** 它算了 `coverage` 却只当展示用，判断
"要不要重编"时只看 manifest diff。实测库里 1781 条输入有 **61 条无任何页面引用**
（最早可追到 09-10），而它一直报"✓ 库未变化"。
→ `coverage.uncovered` 进 message 与返回值。**只告警、不触发重编** —— 否则会
陷入"每次都触发、却因脏会话为空而什么都不做"。

**⑤ 根因是配置漏配。** `wiki.llm` 没有 timeout 覆盖 → 继承默认 **60s**，而 L1 是
长调用：`mcp/direct` 这个直写虚拟会话积累了 101 条记忆，在**分组调用**上连续
3 次读超时（60s × 3 + 退避 ≈ 187 秒），整会话编译失败。第二级早已把 timeout
放宽到 900s（yaml 注释写着"默认 60s 对输入几万字符的归域调用必然读超时"），
**第一级漏配**。→ 默认值本身就是 900s，不再要求使用者先知道这个内部坑。

顺带澄清一个极易误判的数字：`session_fail` 里的 `memories=101` 是**编译输入的
全量**（该会话 11 天的历史库存），**不是**"积压未编译的增量"—— 当时的真实增量
是 `dirty=1`（当天新写的那一条）。触发其实很勤：`first_write_daily` 每自然日
必然命中一次。

**遗留**：`compile_page` 有 fail-open（单组失败不影响其它组），但 `plan_groups`
**没有** —— 分组一失败整会话就废。暂不加"兜底分组"降级：那样的产出质量不可控，
宁可如实失败并重试（① ② 已保证失败可重试、可见）。

**同日第二次定位：耗时 vs「卡死」**。修好 timeout 后重跑，40 多分钟仍无输出，
一度被误判成"又卡住了"—— 并因此**两次杀掉正在正常工作**的编译。用短超时
（90s、不重试）做规模探测才看清：

```
前  3 条（  826 字）：✅ 60.3s
前 10 条（ 6792 字）：✅ 75.9s
前 40 条（27900 字）：✅ 68.2s，分 14 组     ← 分组根本没卡
```

**真正的耗时在逐组编译**：101 条 → 30+ 组，每组一次 LLM 调用（30~90 秒），合计
**30~60 分钟**；而完成事件（`page_done` / `call`）只在整会话结束后才写 —— 全程
在日志里静默。两处修正：

- **分组分批**（`wiki.plan_batch_max`，默认 40）：分组是"**输出规模随输入线性
  增长**"的调用，101 条一次性分组会真的卡到超时；分批后每批约 1 分钟。批内编号
  必须映射回全局编号（`compile_page` 按全局清单取记忆，不映射会越靠后错得越离谱）
- **进度落盘**：`compile_one` 此前把 `log` 整个吞掉，现在逐步写 `wiki.log` 的
  `progress` 事件（"两段式：先分组（101 条，单批上限 40）"→"[分批 1/3] 40 条"→…）

顺带修掉一处"配置形同虚设"：`wiki.single_shot_max` 在 `DEFAULT_WIKI` 与 example
里都存在，**却从未被读取**（脚本用硬编码常量，默认值恰好一致才一直没暴露）——
现在由 `wiki_compile._limits()` 统一取值，非法值回落常量。

**同日第三次改动：并发 + 429 限流**。既然各组之间**无依赖**，串行就是纯浪费 ——
改为 `wiki.page_workers`（默认 3）并发，**结果按组序重排**（完成顺序不确定，直接
append 会让页序随机漂移、产物不可复现）。实测 32 组从约 48 分钟降到约 12 分钟。

并发带来一个新风险：多个 worker 会几乎同时撞上同一个 RPM/TPM 窗口，而**各自独立
退避会在同一时刻一起恢复、一起重试** —— 即"退避共振"，反而更容易持续撞限。所以
429 的处理放在 `agentmemhub/llm.py`（所有链路共用）而不是调用方：

- **进程级共享闸门**：撞到 429 就把"下次允许发请求的时间"推后，**所有线程一起等**
- **尊重 `Retry-After`**（秒数或 HTTP-date；上限 300 秒，防服务端给离谱值把任务卡死）
- **限流多给重试**：总尝试次数放宽到 `max_retries + 1 + 2`（RPM 窗口是分钟级，
  默认 3 次尝试常常不够用）

**同日第四次：切网暴露的两个漏网**。用户切换网络时 L1 有 3 组失败，顺藤查出：

- **`IncompleteRead` 不算瞬态**：它继承自 `http.client.HTTPException`，而 `_post`
  只把 `(URLError, TimeoutError, OSError)` 当瞬态 → **一次都不重试**，网络抖一下
  就直接丢一组。现已把 `HTTPException` 一并纳入瞬态重试。
- **组级失败被 fail-open 吞掉**：单组失败不影响整会话（这本身是对的），但会话仍算
  "成功" → 那几组的记忆**照样被写进新基线** → 与"会话级失败"一样被永久掩盖
  （**同一个坑，粒度更细**：会话 → 组）。实测 23 组里 3 组失败、**20 条记忆**被
  静默丢弃。现在失败组的成员会被报出来、按记忆 id 剔除出新基线，下次增量重试。

**教训**：可观测性的缺口会**反过来制造错误判断** —— 日志静默时，"慢"和"死"
看起来一模一样，排查者会做出破坏性动作。
