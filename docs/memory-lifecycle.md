## 0. 一句话设计

**衰减给记忆标"新鲜度"，命中给它"续命"；冲突检测只标记不执行；
淘汰分四层走、每层可逆，第一期全部"只报告不自动"。**

---

## 1. 问题：数据只增不减的三个缺口

当前库内记忆类 unit 约 2.2 万条（蒸馏 1,916 + 直写投影 + 页面投影），增长无上界。
已就位的：软删除（`wiki_ignore_at`）、wiki 增量、零命中报表（`stale`，2026-11-07）、
命中统计（`recall_hits.db`，2026-11-07）。缺的：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | **衰减参数错配**：现有衰减按"创建时间、半衰期 30 天"算，技术知识半年后权重只剩 1/64；且"被用过"完全不参与 | 老而有效的记忆沉底；新写的记忆刚入库就互相被时间拉开 |
| 2 | **"旧结论被新结论取代"不可见**：内容演进（v2.5→v2.6）在新记忆入库后，旧记忆仍以同等资格参与召回 | 召回结果里新旧结论并排，Agent 无法分辨哪个是当前事实 |
| 3 | **淘汰无标准**：`stale` 报表给出了"零命中"候选，但从"看见"到"处置"之间没有分层路径与判定标准 | 清理要么不敢做（怕误删），要么一步到位硬删（不可逆）|

## 2. 现状机制矩阵（已逐点核实，2026-11-07）

| 机制 | 语义 | 位置 | 生命周期效果 |
|---|---|---|---|
| 初始分 | 蒸馏 0.3 / 直写 0.4~0.8 | `memstore.ensure_base_value` | 起点，不回落 |
| 反馈演化 | 👍/👎 有符号均值重算 value | `set_user_feedback` / `put_feedback` | value ≤ 0 撤出召回 |
| 时间衰减 | `v × 0.5^(Δt/30天)`，Δt=创建时间 | `ext.decayed_value` + `apply_value_boost` | **仅 tie-breaker**（BOOST_CAP=0.3）|
| 手动加权 | `manual_value` 锁定，**不衰减** | `unit_values.manual_value` | no_decay 白名单 |
| 归档打标 | similar（0.80~0.92）/ duplicate（≥0.92）| `distill` S3 | 不再投影/召回（duplicate）或互链（similar）|
| prompt_ver 清理 | 旧提示词版本产物物理删除 | `purge_stale_memories` | 全自动、不可逆（可重蒸馏）|
| 软删除 | `wiki_ignore_at`：不进 wiki、**仍可召回** | `wiki_pending.py` | 手动、可逆 |
| 硬删除 | 蒸馏行+投影+向量删除 | `wiki_pending.drop --mode hard` | 手动、不可逆 |
| 命中统计 | 最终命中记 `recall_hits.db` | `recall_stats.record_hits` | 2026-11-07 起积累 |
| 零命中报表 | `stale --days 90` 清单 | `recall_stats.stale_memories` | 只报告 |

关键代码事实（设计依赖的三个支点）：

1. `apply_value_boost` 对 `v ≤ 0` 的条目**直接剔除**出召回结果
   （`include_low_value=True` 的复盘场景除外）；
2. `ValueStore.values` 返回 `COALESCE(manual_value, value)`——
   **`manual_value` 锁 0 ⇒ 召回面看不见它；清除加权 ⇒ 完整恢复**，且零新表零新列；
3. 衰减参与排序的通道已存在（`rel + min(0.3 × decayed_value, 0.3)`），
   有 `BOOST_CAP=0.3` 有界保护——**升级它比绕开它另开一路风险更低**。

## 3. 设计一：衰减——freshness（新鲜度）

### 3.1 公式与参数

```python
anchor  = max(创建时间, last_hit_at or 0)      # 双锚点：被用过就"续命"
age     = now - anchor
freshness = 1.0                              , age ≤ offset
         = 0.5 ** ((age - offset) / half_life), age > offset
```

| 参数 | 取值 | 理由 |
|---|---|---|
| **offset（保鲜期）** | 90 天 | 刚沉淀的记忆之间不互相拉开；技术知识的"新"以季度计 |
| **half_life（半衰期）** | 180 天 | 1 年后剩 12.5%、3 年后剩 1.6%——老知识沉底但**不归零**，`value≤0` 仍是唯一的"撤出"判据 |
| **锚点** | `max(创建, 最后命中)` | LRU 语义：老而常用的记忆是"经典"不是"过期"。`last_hit_at` 缺失（冷启动）自动回落创建时间，优雅降级 |

与旧参数对比：**30→180 天、单锚→双锚、无保鲜→90 天保鲜**。
方向不变（指数衰减、有界 tie-breaker），只修参数与锚点。

### 3.2 用在哪、不用在哪

| 用途 | 用法 |
|---|---|
| **召回排序**（升级既有通道）| `apply_value_boost` 内部改用 freshness：`rel + min(0.3 × freshness(v), 0.3)`。BOOST_CAP 语义不变，正反馈自激天然有界（见 §3.3）|
| **stale 报表排序** | 排序键从纯时间改为 `value × freshness`（低分老记忆排最前）|
| **淘汰判定** | freshness + 零命中时长共同决定分层候选（§5）|
| **展示层标注** | 面板/溯源浮层显示"沉淀于 N 天前，最后命中 M 天前"——**提示而非隐藏** |

### 3.3 正反馈自激的有界性（为什么命中可以续命）

"被召回 → 续命 → 更靠前 → 更容易被召回"的环路存在，但增益有硬顶：
boost 上限 0.3，freshness 上限 1.0，且**主排序是相关性**（六路融合名次），
价值只做同分簇内的次级权重。自激最多把一条记忆从"排序边缘"抬到"簇内靠前"，
抬不进不相关的查询——相关性与价值解耦的既有设计（recall-fusion.md 的核心结论）
恰好挡住了失控路径。观察期后如有"热门记忆霸屏"迹象，可引入**命中衰减折扣**
（每次续命只回 90% 的保鲜期）——列为备选，不进第一期。

### 3.4 改造点（精确到行）

| 文件 | 改动 |
|---|---|
| `rag/ext.py` | `decayed_value` 加 `offset_days` 参数（默认 0 兼容既有调用方）；`HALF_LIFE_DAYS 30→180`；新增 `FRESH_OFFSET_DAYS=90` |
| `rag/search.py` ~815 | `meta` 构造处把锚点换为 `max(units.time, last_hit_at)`：候选 ids 一次查 `recall_hits.db`（ATTACH，文件不存在跳过）|
| `rag_bridge.py` | 无需改（`no_decay_ids` 语义不变：⭐ 锁定的仍不衰减）|
| `recall_stats.py` | `stale_memories` 排序键改 `value × freshness`，返回列加 `freshness`、`last_hit_at` |

### 3.5 配置策略（暂不加配置键）

半衰期/保鲜期先用**模块常量**，不进 `agentmemhub.yaml`。理由：本项目在
"配置键没有消费点/值恰等于默认值"上踩过四次（`wiki.enabled` 等），新键的
维护成本（example 同步 + `check_config_keys` + 体检）只有出现**真实调参需求**
（≥2 个场景要求不同参数，比如"行情类记忆要 7 天半衰期"）后才值得付。
文档写明常量位置，升键条件记录在案。⭐ 锁定值与 `no_decay` 白名单机制已保证
用户对单条记忆的意志永远优先于全局参数。

## 4. 设计二：冲突检测（矛盾检测的分层方案）

### 4.0 先回答"是不是只能 LLM"——不是

LLM（Mem0 的 ADD/UPDATE/DELETE/NOOP 四操作）是**开放域**的通用解。
个人/团队知识库的记忆有强结构性——绝大多数"矛盾"是**同一事实的版本演进**
而非语义对立，且人表达"更新"时几乎总会留下语言标记（"改为/废弃/不再"）。
规则层（零成本、可解释）能抓住大头，LLM 只兜剩余的高价值不确定项。

### 4.1 四层漏斗

```
L0 候选生成（向量近邻，已有基建）    2.2 万条 → 每条 top-10 候选对
L1 变更词规则（零成本）              抓 70~80%：显式版本演进/否定
L2 结构化槽位对比（零成本）          抓配置类矛盾：同槽位不同值
L3 本地 NLI 小模型（不进第一期）      语义对立、无表面标记——误报不可解释
L4 LLM 判定（按需，兜底）            仅对高价值 open 项，人工确认后执行
```

**L0 候选生成**：
- 增量：蒸馏投影 / Agent 直写落库钩子内，对新 unit 用 active 向量查 top-10 近邻
  （sqlite-vec KNN，单条毫秒级），相似 ≥0.80 的成对；
- 存量：CLI 离线批扫（`conflicts --scan`），2.2 万次 KNN 估分钟级，跑一次即可；
- 复用 S3 既有 similar 互链（`dedup_of`）作为补充候选源。

**L1 变更词规则**：新记忆含变更标记词，且与某旧记忆相似 ≥0.85：

```
中文：改为/换成/替换为/迁移到/不再/停用/废弃/弃用/取消/回退到/纠正/其实不是…
英文：deprecated / removed / no longer / instead of / replaced by / reverted…
```

命中 → 判定 kind=`evolution`（演进对：新条目疑似取代旧条目）。

**L2 槽位对比**：对候选对各自跑 `extract_identifiers`（已有）+ 数字抽取：

- 同槽位不同值（`8086` vs `9100`、`0.92` vs `0.85`、路径/模型名）→ kind=`conflict`；
- 版本号演进（`v2.5` vs `v2.6`）→ kind=`evolution`（非矛盾，但标注"有新版本"）；
- 仅修饰词不同 → 不报告（交给既有 S3 判重）。

**L3（缓做）**：本地 NLI（mDeBERTa 级，~500MB）CPU 每对 50~200ms、
中文误报不可解释——**等 L1+L2 跑一个月，看实际漏报再决定**。文档记录此决策。

**L4（兜底）**：open 状态的候选对按 `value` 排序取 Top N 交 LLM 判定，
结论仍进人工确认队列——LLM 也可能错，不自动执行。

### 4.2 数据模型（新表，索引库）

```sql
CREATE TABLE IF NOT EXISTS memory_conflicts(
  id INTEGER PRIMARY KEY,
  unit_new  INTEGER NOT NULL,   -- 新（疑似取代方）
  unit_old  INTEGER NOT NULL,   -- 旧（疑似被取代方）
  kind      TEXT NOT NULL,      -- 'conflict' | 'evolution'
  rule_hit  TEXT NOT NULL,      -- 命中证据：'l1:改为' / 'l2:slot=port 8086≠9100'
  similarity REAL,
  status    TEXT NOT NULL DEFAULT 'open',
             -- open | superseded（旧已归档）| kept_both（都不动）
             -- dismissed（误报，附 dismiss_reason）
  detected_at INTEGER, resolved_at INTEGER, resolved_by TEXT
);
CREATE UNIQUE INDEX idx_mc_pair ON memory_conflicts(unit_new, unit_old);
```

**只标记、不执行**。处置动作全部复用既有能力（§5），不新发明删除语义。
表放 `session_rag.db`（引擎域：读写都走索引库连接，与 `distill_hashes` 同级）。

### 4.3 误报治理

- 每条候选对带**证据链**：哪层规则、命中什么词、相似度、槽位 diff——面板上一眼可判；
- `dismissed` 保留记录（不删行），同一对永不重复报告；
- dismissed 达到一定量后**回顾规则**（某 marker 误报率高就从清单撤下）——
  规则清单可热改（与 `feed` 格式白名单同模式）。

## 5. 设计三：分层淘汰（每层可逆，第一期只报告）

```
                     ┌─ 人工确认前，任何自动动作都不发生 ─┐
Tier 0  报告      stale 报表（已上线）：零命中 + freshness 排序          [只读]
Tier 1  归档      manual_value 锁 0：撤出召回面、数据完整保留、⭐即恢复  [可逆]
Tier 2  隔离      wiki_ignore_at：不进 wiki、仍可召回（既有软删除）      [可逆]
Tier 3  硬删      蒸馏行 + 投影 + 向量物理删除                          [不可逆]
```

### 5.1 为什么中间层用 `manual_value 锁 0` 而不是新概念

§2 支点 2 已核实：`manual_value=0` ⇒ `COALESCE` 后 v=0 ⇒ `apply_value_boost`
硬剔除；清除加权 ⇒ 立即恢复。它天然满足"撤出召回面、可逆、用户意志（no_decay）
优先"三重要求，**零新表零新列零新代码路径**——第一层淘汰直接复用面板 ⭐ 的
既有 UI 与 API（`POST /api/engine/weight`）。`include_low_value=True` 的复盘
场景仍能看见归档条目（有意保留的出口）。

### 5.2 判定标准（候选生成，非自动执行）

一条记忆进入 Tier 1 候选，需同时满足：

- 创建已满 90 天（保鲜期外）；
- 最近 90 天零命中（`recall_hits` 无记录或 `last_hit_at` 早于窗口）；
- freshness < 0.5（即锚点年龄 > 90 + 180 天）；
- `memory_conflicts` 里不是任何 `superseded` 对的**旧方**（被取代的旧结论
  应优先归档——这把冲突检测与淘汰接成闭环）。

满足即进"建议归档"清单，**人工在面板逐条或批量确认**。自动归档列为远期
（默认关闭的配置键 + 干跑日志，等跑稳两三个周期再议）。

### 5.3 与 `memory-deletion.md` 的衔接

Tier 3（硬删）对"已进 wiki"的记忆**必须走那份设计的墓碑 + 引用重映射**，
本文不重复设计；对"未进 wiki"的记忆走既有 `wiki_pending.drop --mode hard`。
实施顺序上：本设计 M1~M3 不依赖墓碑表；如果用户在 Tier 3 前只做 Tier 1/2，
`memory-deletion.md` 可以继续缓——**分层方案让重的那块（墓碑）不再阻塞轻的那块（归档）**。

## 6. 入口设计

| 入口 | 形态 |
|---|---|
| **CLI** | `stale`（已上线）扩展 `--suggest-action`：按 §5.2 标注建议层级；新增 `conflicts [--scan] [--status open] [--resolve]`：扫描 / 列表 / 处置 |
| **HTTP** | `GET /api/lifecycle/stale`（报表数据源）、`GET/POST /api/lifecycle/conflicts`（列表与处置）。归档/恢复复用既有 `/api/engine/weight` |
| **面板** | 记忆报表页新增「生命周期」视图：stale 清单（按建议层级分组）+ 冲突队列（证据链展示 + 二选一按钮）。**所有处置动作二次确认**（面板既有纪律）|
| **日志** | 新事件登记 `docs/logging.md`：`conflict_detected`（层/规则/相似度）、`lifecycle_archive`（unit/层级/操作者）|

MCP 侧**不加**新工具：处置是人工决策，不给 Agent 无人值守入口
（与"投喂不给删除"同一纪律）；只读的冲突查询可后续按需加。

## 7. 明确不做的（第一期）

- **不做自动归档/自动删除**：所有处置动作人工确认（数据是派生物，但重蒸馏花钱且会漂移）；
- **不做命中加分**：命中只用于续命（freshness 锚点）与零命中判定，不写 `unit_values`——避免"高频召回→高分→更易召回"进反馈账本；
- **不做 NLI**：等规则层数据（§4.1 L3）；
- **不加配置键**：§3.5；
- **不动 `priority` 语义**：`max(old, abs(value))` 只升不降的问题在评分语义
  重排时一并解决（audit §4.5-4，已挂起等业务口径），本设计绕开它而不修它。

## 8. 里程碑与验收

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M1** 衰减升级 | freshness 双锚点 + 保鲜期 + 半衰期 180（§3.4 改造点）| 全量回归绿；新增测试：同龄记忆"最近被命中的 boost 满、从未命中的按新半衰期衰减"；⭐ 锁定值仍 no_decay |
| **M2** 冲突检测规则层 | `memory_conflicts` 表 + L1/L2 规则 + 存量 `--scan` + CLI 列表 | 存量扫描跑通（记录耗时）；人工抽样 50 对，准确率 ≥ 80%（低于则先调规则不加层）|
| **M3** 面板生命周期视图 | stale 按建议层级分组 + 冲突队列 + 归档/恢复按钮 | 路由↔前端对账脚本通过；处置动作二次确认有测试 |
| **M4**（可选） | NLI 或 LLM 兜底；自动归档（默认关） | 依据 M2/M3 运行数据再立项 |

M1/M2 相互独立可并行；M3 依赖 M2 的表结构。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| `recall_hits` 冷启动：老记忆 `last_hit_at` 全空 | 锚点自动回落创建时间（已实现）；stale 报表冷启动≈全量属预期，已写进 CLI 文案 |
| freshness 改动影响既有召回质量 | BOOST_CAP 有界保护不变；用既有召回测试集回归；异常随时可回滚（两处小改动）|
| 冲突规则误报骚扰 | 证据链 + dismissed 留痕 + 规则热改（§4.3）；首期只在 CLI 出报表、不进面板推送 |
| 存量扫描 O(n²) | 已排除：ANN top-10 近邻（每条一次 KNN），批扫一次几分钟量级 |
| 归档后"删了还能搜到"类心智混乱 | 归档条目在面板有显式状态徽章；`include_low_value` 复盘出口文档化 |

### 11.3 ⚠️ 实测教训：规则层的精度是磨出来的（四轮收敛）

这是本文最有价值的一节——**初稿 §4.1 的四层漏斗在真实库上几乎全是误报**：

| 轮次 | 检出对数 | 抽样准确率 | 根因 |
|---|---|---|---|
| 1 | 2823 | 极低 | 数字槽位混桶（"3 分钟" vs "4897 条"）；双投影 `mcp_/dst_` 互相命中 |
| 2 | 2534 | 低 | 加"唯一值"约束后 conflict 1633→657，但 L1 变更词独立触发 |
| 3 | 1633 | 低 | evolution 1557 对：**变更词在技术记忆里太普遍** |
| 4 | 95 | ~8% | 只留版本/端口，但裸版本号在不同主题间毫无可比性 |
| **5** | **0** | **无噪音** | 版本号**绑定主体名**；`model` 与裸版本号全部降级为证据 |

**五条硬结论**（后续改这块必读）：

1. **变更词不能独立触发**。技术记忆几乎每条都在描述变更（"2026-10-07 从 X
   改为 Y"），把"含变更词"当取代证据会产出千级噪音。它只能作 `detail` 证据。
2. **数字差异不能独立触发**。"M1 完成共 106 条" vs "M3 完成共 5 条" 是不同
   里程碑的数量，不是同一配置项的两个候选值。可靠判定数字归属需要语义理解。
3. **`owner/name` 形态不等于模型名**。GitHub 仓库、分支名（`feat/xxx`）、
   参数对（`p1/p2`）、数值对（`0.873/0.659`）全都长这样。
4. **版本号必须绑定主体**。裸 `v1.2.3` 在不同主题的邻居之间必然"不同"，
   只有 `Mobile_App_AutoTest v1.1.0` vs `v1.4.0`（同主体）才是真换代。
5. **双投影必须排除**。`mcp_<h>` 与 `dst_<h>` 是同一内容两份投影，
   sim 恒为 1.000，且会因排序靠前而污染列表首屏。

收敛后的**可用信号只剩两类**：① 同一主体的版本换代（`ver:<主体>`）；
② 唯一端口冲突（`port`，要求两侧都只出现 1 个端口值）。

**代价是漏报**：当前真实库扫出 **0 对**——不是坏了，而是这个库里
确实没有"同主体版本换代/端口冲突"的候选。想覆盖"表述不同但确实取代"的
情形，只能靠 L4（LLM 兜底，按 `value` 排序取 Top N）。**这正好验证了
§4.1 的设计取向：规则层负责高精度低召回，LLM 负责高召回。**
