# feed — 外部投喂转译层

> 设计文档：[`../feed-adapter-plan.md`](../feed-adapter-plan.md)（v2.2 + 六轮实施记录，**为什么这么设计**）
> 本文是**模块文档**：职责边界 / 数据形态 / 怎么用 / 怎么排查（**改代码前先读它**）
> 状态：**M0–M5 全部落地**（2026-10-16，tag `feed-m5`）；**面板入口已落地**（2026-10-22，
> 分两期：只读视图 + 写入/删除）。这条线只剩 **T4 图片 OCR**（用户指定放后）

> **30 秒速览**：把外部素材（文件 / 网址 / 正文）转译成统一 markdown，发布到**与自有
> wiki 并列**的知识库页面层（`origin=external`），**不进**记忆 / 蒸馏 / wiki 编译。
> 已适配：md·txt / 网页（含本地另存）/ 公众号 / PDF（四路由）/ DOCX / PPTX / XLSX /
> XMIND / CSV·TSV。
> 三个入口：**CLI**（`feed` 子命令）· **HTTP**（`/api/feed/*`，11 个）·
> **MCP**（`feed_add` / `feed_list` / `feed_status`）。
> **功能与参数总览在 §7**（"时间长了忘了就来对一遍"）；配置项只有 5 个键。

## 1. 职责边界（别和 `adapters/` 混）

| | `agentmemhub/adapters/` | `agentmemhub/feed/`（本文） |
|---|---|---|
| 干什么 | **采集**内部 Agent 会话 | **转译**外部素材 |
| 输入 | DSH / Qwen / ZCode… 的会话存档 | 本地文件 / URL / PDF / 图片 |
| 输出 | `conversations` + `events`（源库） | 统一 md（**交付物**）+ 登记表 |
| 下游 | 摄取 → 蒸馏 → wiki 编译 | **知识库页面层**（与 wiki **并列**，不进编译链） |

两者形态同构（注册表 + 认领 + 统一产物），但数据流方向与服务对象完全不同，**不合并**。

**并列的含义**（用户 2026-10-10 拍板）：投喂内容**不进**记忆/蒸馏/wiki 编译 ——
它只以"知识库页面"的形态存在，召回时与自有 wiki 页面同台竞争（`origin` 维度可区分）。

## 2. 三段物料（用户明确要求的三份保留）

```
第 1 段  raw/      不可变原件字节，**内容寻址** raw/<sha256 前 2 位>/<sha256>.<ext>
第 2 段  mirror/   转译中间形态，按 doc_id 归档（HTML 源码 / 渲染快照 / OCR 中间态）
第 3 段  kb/       最终 md（**统一交付物 / 知识库本体**）—— 默认 exports/wiki_work/out_feed/
```

三个位置由 `feed` 配置段给出（`db` / `store_dir` / `kb_dir`），
经 `Config.feed_paths()` **统一解析成绝对路径**（三处必须同源，否则会写出
"原件进 A、登记表指向 B"这类错位）。

**为什么原件走内容寻址的文件系统而不是塞进库 BLOB**：溯源强度由 hash 锚保证，不必把字节放进库里
——而库一旦进快照，每份快照都要复制一遍素材（×`snapshot.keep` 放大）。内容寻址顺带带来两个好处：
**同内容重复投喂天然去重**，且文件可被任何工具直接打开。

**`materials.db` 是独立库且不进快照轮换**：它只是"元数据 + 指针"，丢了能从 `raw/` 重建
（原件才是不可再生的那一份）。

## 3. 数据结构
### 3.1 `FeedDocument`（转译层**对内唯一契约**）

所有转换器的输出都收敛成它（`feed/base.py`）：

| 字段 | 说明 |
|---|---|
| `doc_id` | 内容锚 = `sha256(原件字节)[:16]` —— **同字节 ⇒ 同 doc_id**（幂等的根） |
| `title` / `markdown` | 标题 / **最终 md**（统一交付物） |
| `kind` | `text` \| `url` \| `wechat` \| `pdf` \| `image` |
| `source_ref` | 原始路径或 URL（人可读的"从哪来"） |
| `doc_time` | **文档自身时间**（发布/修改），**不是投喂时刻** —— 时间衰减按它算 |
| `mirror` / `converter` | 镜像文件表 / `名字@版本`（**重转判据**） |
| `quality` / `warnings` | 质量自评：既是给人看的指标，也是"要不要升级到 LLM 兜底"的**触发器** |

**空正文直接 `FeedError(kind="empty")`** —— 空页面会变成"标题正当、内容为空"的召回单元。

### 3.2 `materials` 表（登记表 + 状态机）

```
received ──convert──▶ converted ──publish──▶ published
    └────────────── failed ◀──────────────┘（retracted：撤下交付物但原件保留）
```

`failed` **不删原件** —— 换转换器版本后可以 `feed retry`（这就是三段保留的价值）。

## 4. T2：网页与公众号（M3 已落地）

**实测驱动的三条**（2026-10-12，用真实链接）：

| 结论 | 证据 |
|---|---|
| **UA 是硬需求** | 同一公众号链接：不带浏览器 UA 只拿到 **18 KB 桩页**，带 UA 拿到 **3.6 MB 真页** |
| **trafilatura 够用，不必自写抽取器** | 公众号抽出 3,492 字 + 正确标题 + 发布日 `2024-09-26`；文档站 84,737 字 |
| **信噪比 0.1%** | 3.6 MB 真页里可见文本只有 4,320 字 ⇒ 把原件喂模型 ≈ 90 万 token 换 4 KB |

> **修正一个预判**：计划原以为"公众号必须特化解析"。实测反过来 —— 它的 DOM 极其规整、
> trafilatura 直接就能抽；**难点在"访问"（反爬/UA），不在"解析"**。所以 `wechat.py`
> 只做两件事：**定向兜底**（通用抽取太短时切 `#js_content`）与**发布时间解析**。

**三级取回**：① 脚本直抓（httpx，走代理）→ ② Playwright 渲染（**尚未实现**）→
③ **人工兜底**：`feed add --stdin`（粘正文）或浏览器另存 HTML 后 `feed add`。
检测到反爬/异常页**不硬闯**，报错直接给兜底指引（反爬是军备竞赛，兜底是一等公民）。

> ⚠️ 第 ② 级原先预留了 `feed.fetch.renderer` 开关，但它**没有任何读取点** ——
> 2026-10-15 实测确认后连同 `feed.convert.llm` / `feed.convert.ocr` / `feed.depth_default`
> 一起删除（见 §11 不变量 25）。**报错文案也不许再指引它**：指向一个不存在的开关，
> 用户会去改它、然后发现毫无反应。

**图片**：trafilatura 的 markdown **实测会丢图**（真页 14 张 `<img>` → 0 张），
所以本地化做在 **HTML 层面**：下载进 `mirror/<doc_id>/images/` 并改写 `src`；
`mirror/index.html` 存**抓到的原始源码**，改写版另存 `localized.html`；
抽取器丢图时**如实记警告**（不静默失真）。

**两个易错点**（都有测试）：
· **URL 的身份是"最终 URL"，不是内容 hash** —— 动态页面字节每次都变（时间戳/CSRF），
  按内容判会"每投喂一次多一条"；
· **`var ct` 不是发布时间**（更接近渲染时刻），真页也没有 `#publish_time` 元素
  （只出现在 URL 编码的 JSON 里）⇒ 以 trafilatura 元数据日期为准。

### 4.1 本地另存的网页（**M3 承诺过、当时根本走不通**）

`feed add 某页.html` 这条兜底通路在 M3 的文档里写着，但 `UrlConverter.can_handle`
当时**只认 `http(s)://`** ⇒ 那条路实际走不通。2026-10-15 扫用户文档目录时暴露：
**61 个本地 `.html` 一个都进不来**。现在按扩展名（`.html/.htm/.xhtml`）或字节
（无扩展名的报告页，靠 `<!doctype html>` 认）认领，与网络抓取**共用同一套抽取逻辑**，
只在三处分叉：

| 分叉 | 网络页 | 本地另存页 |
|---|---|---|
| 图片相对路径 | `urljoin(page_url, src)` + 下载 | **按文件所在目录读文件系统**（`meta.base_dir`） |
| 文档时间 | HTTP 头 / 页面元数据 | **文件 mtime**（本地文件没有 HTTP 头，`now` 会让旧资料显得"刚产生"） |
| `kind` | `url` | `html`（它**不是** URL，别混） |

⚠️ 顺带修掉一个 **M3 就埋下的缺口**：`_HTML_IMG_RE` 原来硬编码了 `https?://`，
于是**相对路径的图片从来没被本地化过** —— 公众号恰好全用绝对 URL 才没暴露，
普通网站（`/static/a.png`）与本地网页则一张图都留不下。

### 4.2 内嵌数据抢救：数据在文件里、不在正文里

真实素材：60 份"脚本录制工具"导出的测试报告，HTML 157 KB、**静态可见文本只有 136 字**
（全是「用例名称:」这类字段标签），真正的数据是 `<script>` 里的
`var resultData = {…}`（27 KB）。

而质量自评按"**抽取覆盖率**"算，给这种页面打了 **1.00** —— 抽取确实覆盖了全部可见文本。
**覆盖率 ≠ 信息量**：不处理的话，知识库里会躺 60 个看起来正常、实际是空壳的页面。

处置原则：**先取回，取不回才打标**。

1. **把数据取回来**（`feed/embeddata.py`）：用 `json.JSONDecoder.raw_decode` 解析内嵌
   JSON（它能从任意位置精确解析**一个完整值**，天然处理嵌套与字符串里的括号 ——
   正则做这件事必然在大对象上出错），把 `list[dict]` 渲染成表格，并去掉裸标签骨架。
   实测 **51/61 救回**，最高一份从 424 字变成 **18,523 字**；
2. 取不回（数据本就是空、或页面确实没内容）⇒ **质量降到 0.4 + 给出可执行指引**
   （从源系统重新导出 / 浏览器里另存为完整页面），不让空壳冒充满分。

⚠️ **触发条件刻意很窄**：只在"正文是空壳"（`looks_like_label_shell`：以冒号结尾的短行
占比 ≥ 30%）时才动手 —— 通用地从网页里挖 JSON 很容易挖出一堆无关配置（主题、埋点、路由表）。
**宁可漏救，不可乱灌。**

⚠️ 一个"阈值定太严"的教训：`MIN_DATA_BYTES` 最初写 2048，把**记录本来就少**的报告误判成
"没数据"（一份只有 3 条记录的报告是 1049 字节）⇒ 60 份里 16 份没救回来。
判据应该是"**能不能渲染成表格**"，字节数只用来挡碎片 —— 现在降到 256。

## 5. T3 · PDF（M4 已落地）

**"PDF 不是一种东西"** ⇒ `pdf.py` 的职责是**先探再派**（`probe → route`），不是一个解析器：

| 亚型 | 客观判据 | 处置 | 产出 |
|---|---|---|---|
| **T3a** 文字版·单栏 | 每页 ≥ 50 字符、无线条表格 | `pypdf` 抽文本层 | 近乎无损（`quality=1.0`） |
| **T3b** 文字版·含表格 | `find_tables()` 命中 | `pypdf` + `pdfplumber` 重建表格 | `quality=0.85`（表格有重构损耗） |
| **T3c** 扫描件 | 平均每页 < 50 字符 | 逐页渲染进 `mirror/<doc_id>/pages/` | **报 `needs_ocr`**（本档不产正文） |
| **T3d** 加密 | `is_encrypted` 且空密码打不开 | 直接报 `encrypted` | 要密码，**不硬闯、不猜** |

判据全部**客观可算**（不看文件名、不猜来源）—— 真实素材上"猜来源"必然出错，
而错判的后果是**静默失真**：把扫描件抽成空正文、把表格抽成散乱文字，
两者都"看起来成功了"。

**⚠️ 一处硬顺序约束（被加密夹具实测逼出来）**：加密档**不能先碰 `len(reader.pages)`**——
未解密就访问会抛 `FileNotDecryptedError`，加密档会变成 `crash` 而不是可处置的 T3d。
所以流程必须是"先判加密 → 再谈页数"
（`tests/test_feed_pdf.py::test_探针_加密档_判_T3d_且探针本身不抛异常` 守它）。

**表格区域剔除是"危险操作"，配了两道闸**：`pdfplumber.extract_text()` 里**包含**表格文字，
不剔除的话同一批字会以"流式正文 + 表格"两种形态各出现一次；但剔除是从正文里**删东西**，
所以：

| 闸 | 内容 | 拦住的真实事故 |
|---|---|---|
| ① **表格要有意义** | ≥2 行且 ≥2 列 | 一行等宽字体代码被误检成"1 行 2 列"，照单全收会把那行**从正文删掉**，而它又不足以构成表格 ⇒ **内容两头落空、永久丢失** |
| ② **剔完要不丢字** | `剔除后正文 + 表格内容` 必须覆盖原页全部字符（多重集比较，容忍 2 字） | 表格 bbox 里的字有一部分没进 `extract()` ⇒ 被剔掉却无处可去 |

闸②不过就**放弃剔除**（保留完整正文、接受表格文字重复）并如实记 warning ——
**重复很难看，丢字是数据事故**，两者代价不对称。
另：`tables_skipped` 会记进 `meta`（"看见了但没当表格"必须可查），但**不记 warning**
（没有造成失真，不该把整篇标成低质量）。

⚠️ 校验必须**同源**：拿 pypdf 的文本跟 pdfplumber 的过滤结果比，光空格处理差异就会被判成
"丢字"，于是永远不敢剔除（闸②形同虚设）。所以 T3b 路由下整篇正文统一改用 pdfplumber。

**能力边界（明说，不假装）**：
· **公式拿不回来** —— PDF 里的公式是排版符号而非语义，任何解析器都一样（C 维度结构性上限）；
· **页内图片位置不保留** —— 文本层不含图片坐标，抽出的内嵌图只落 `mirror/`；
· **T3c 未接 OCR** —— 只做到"探测 + 渲染 + 指路"，OCR 属 T4。

**真实素材验收**（两份，都是用户提供的真实文档）：

```
① Intel_Proprietary_License.pdf   86,805 B  → T3a · 2 页 · 10,333 字 · 质量 1.00
② 文字文稿1.pdf                    325,136 B → T3a · 2 页 · 1,582 字 · 质量 1.00
```

真机共抓到 5 处**夹具永远不会暴露**的缺陷（前两条来自 ①，后三条来自 ②）：
① 元数据 `/Title` **被写坏了**（停在 `…[v2022.12`，正文首行才是完整的 `…[v2022.12.20]`）
⇒ 加了"首行更完整则采用首行"的相似度判据（**不能用"谁更长"**：截断的元数据标题
因为多了 `C2A … (Commercial Use)` 反而更长）；
② `/CreationDate` 末尾的 `Z` 被旧实现丢掉、又按本地时间解释 ⇒ `doc_time` **偏 8 小时**
（时间不是装饰，召回侧的时间衰减按它算）；
③ **误检表格吞掉正文**（最严重，见上表闸①）：`page.get_by_role("button", name="Submit")`
一整行从知识库里消失了，而它本该是这份文档里最有技术含量的一句；
④ **首行被行宽硬切**：`…今年有六年有余的工作经` + 第二行的 `验。`
—— 直接拿首行当标题就是一句断掉的话（现在会缝合，中文不补空格、英文补）；
⑤ **标题取成了 WPS 默认文件名「文字文稿1」**（那份 docx 完全没用标题样式）。

**依赖与许可（计划 §10.2 的 R2 就此结案）**：`pypdf`(BSD-3) 进主依赖；
`pdfplumber`(MIT) + `pypdfium2`(**BSD-3/Apache-2.0**) 进可选档 `feed-pdf`。
**渲染没有用 PyMuPDF**（AGPL-3.0，有传染性）—— `pypdfium2` 是许可完全宽松的替代品，
也不用像 `pdftoppm` 那样在 Windows 上额外分发可执行程序。
缺可选档时**不静默降级**：T3b 退化为 T3a 并记 warning、T3c 报 `needs_renderer`
并给出 `uv sync --extra feed-pdf` 指引。

## 6. DOCX · PPTX · XLSX · XMIND · CSV（**结构就在文件里**的五种格式）

**`.docx` 不属于"PDF 那一类"**（计划 §7.0.1 专门纠正过这个误判）：它本质是 ZIP + XML，
标题/大纲级别/表格/图片**本来就在文件里**；`python-docx` 是确定性抽取 ——
零 LLM、零猜测、可复现，与 T1 同级。把它按 PDF 估工期是这份计划早期最贵的误判。

**最大的坑：段落与表格在 XML 里是兄弟节点且交错。** `document.paragraphs` 与
`document.tables` 是**两个独立列表**，分别遍历会让表格全部挤到文末、文档顺序全丢。
必须按 `w:body` 的子节点顺序走（`iter_block_items`）。夹具 `sample.docx` 里
"表格前后的段落"就是这个坑的哨兵 —— 顺序错了那条断言立刻红。

| 风险 | 处置 |
|---|---|
| **样式名不确定**（中文版 Word 是 `标题 1`，自定义样式名千奇百怪） | 判据落在 **`w:outlineLvl`**（大纲级别才是标题的本质属性）+ 中英样式名兜底 |
| **完全没用标题样式**（标题落到文件名上，而那是 WPS 的默认名「文字文稿1」） | 标题多一档**正文首段**兜底 + 默认文件名判为 junk —— 见下 |
| 超链接里的文字 | 不用 `paragraph.text`（**漏掉 `<w:hyperlink>` 里的 run**），按 XML 取全部 `w:t` |
| 合并单元格 | markdown 管道表表达不了 ⇒ **如实打标**并把质量降到 0.85（不静默） |
| 图片 | docx 有**真实位置**（`w:drawing` 就在某个段落里）⇒ 插回原位，比 PDF 那一档强 |
| `.doc`（97-2003） | **根本不是 ZIP**，`python-docx` 读不了 ⇒ 显式拦住并给"另存为 `.docx`"指引（不报"文件损坏"这种误导性错误） |

**标题兜底的档位**（判据单点在 `feed/titles.py`，PDF/DOCX 共用）：
`core title` → 首个一级标题 → **正文首段** → 文件名 → 占位标题。

为什么必须有"正文首段"这一档（真实素材逼出来的）：一份求职 docx **完全没用标题样式**
（38 段全是正文）、core title 也为空 ⇒ 标题落到了文件名上，而那是 WPS 的默认名
「文字文稿1」—— **默认文件名比正文首段更没有信息量**（前者对所有这类文档都一样）。
首段要**限长**（60 字），限长或占位时都会记 warning：一个像是原文、其实是半句话的标题，
比一个明显是占位的标题更危险。

**两个假告警/真告警的教训（都在真实素材上暴露）**：
· **假告警比漏报更伤**：合并检测最初用 `id(cell._tc)` 比对象身份，而 lxml 的元素代理
  **不保证身份唯一** ⇒ 普通 3×3 表格被误判"有合并"、质量分 1.0→0.8；改判
  `w:gridSpan > 1` / `w:vMerge` 存在；
· **文案不能自相矛盾**：`low_quality` 的语义是"质量分低 **或** 有告警"，而控制台一度打成
  「质量偏低（1.00）」—— 两者必须分开说。

**合并单元格：markdown 里"留空"比"重复"正确**（真实素材命中 3/4 的 docx）：
`row.cells` 对合并区域会把**同一个格子返回多次** ⇒ 整行合并的标题在表格里被复制 3 遍，
读起来像文档写错了。正确呈现是"内容写第一格、其余留空"（`w:gridSpan > 1` 补空列、
`w:vMerge` 续格留空）—— 读者由此看出"这几格是一体的"。
⚠️ "是否含合并"与"怎么渲染"必须**一次遍历产出**：两个判据分开写必然漂移，
一边说"有合并"、另一边按无合并渲染，质量分就与实际呈现对不上。

**真实素材验收**（两份）：

```
① Word 12.0 原生另存的 docx   43,115 B  → 标题层级/顺序/表格/列表/图片全对 · 1.00
② 文字文稿1.docx              153,014 B → 1,657 字 · 质量 1.00 · 标题=正文首段
```

② 是本机没有真实 docx 时，用 **Word 原生另存**（COM 打开夹具 → `SaveAs`）造出的
"真实 Word 签名"样本；后续用户给的真实 docx 又把"默认文件名当标题"这条补上了。

### PPTX · 演示文稿（与 DOCX 同类：OOXML，确定性、零 LLM）

`python-pptx` 读出**分页 + 版面层级**。与 DOCX 的两处差别要单独处理：

| 差别 | 处置 |
|---|---|
| **页是作者刻意分的结构**（不是排版折行） | 每页一个 `## 第 N 页：<标题>` |
| **备注常常比正文更有信息量**（讲稿、补充说明） | 一定取 `slide.notes_slide`，以 `> 备注：…` 附在页末 |

能力边界（明说，不假装）：**图文分离** —— 图片落 `mirror/`，但"画在第几行"表达不出来
（PPT 是**版面**不是流式文档，形状靠坐标定位）；**图表只取数据不取"说明了什么"**
（后者是 T4c 多模态的活，不在这里硬凑）。

⚠️ **一个假告警（写测试时踩到）**：最初对每个"没有文字的形状"都试 `shape.image` ——
线条、自选图形、空文本框会抛异常，于是 8 页的 PPT 报出「8 张图片读取失败」（实际只有 4 张图）。
改成**先判形状类型**（`MSO_SHAPE_TYPE.PICTURE`）再取图。同一条道理第二次出现
（第一次是合并单元格的 `id(cell._tc)`）：**假告警比漏报更伤**。

⚠️ **另一个判据坑**：判"这份 PPT 基本是图"要用**占比**而不是绝对页数 ——
单页 PPT 必然只有 1 页有文字，拿"≤1 页"去判会把一份正常的一页 PPT 判成"正文都在图片里"。

**真实验收**：4 份 PPT（最大 130 MB / 36 页）全部成功；标题一律回落文件名
（core title 全是「PowerPoint 演示文稿」这个默认值）、表格 4–5 张、图片按张落 `mirror/`。

### XMIND · 思维导图（零依赖：ZIP + JSON/XML）

思维导图是**结构化知识的原生形态** —— 分支与取舍天生带层级，正是纯文本最难表达的。
用户 14 份业务导图里最大的一份有 **20 个画布 / 2861 个主题 / 94,173 字**。

**⚠️ 解析顺序不能反**：新版（XMind 2020+）用 `content.json`、旧版（XMind 8）用 `content.xml`，
而实测那 14 份**两个文件都有**、`content.xml` **全都是同一份 4,309 字节的空壳**
（旧版兼容留的占位）⇒ 先读 xml 会得到一份"看起来成功、实际空"的导图。**先 json 后 xml。**

处置细节：

· 层级 → markdown **嵌套列表**（2 空格/级）；备注/标签/超链接**压成行内**
  —— 换行会打断嵌套列表的层级；
· **单画布不加 `## 画布` 小节**：导图名就是文档标题，再加一层纯属重复（同 PDF"单页不加页码"）；
· 多画布才按画布分节，并说明"跨画布的关系线未保留"；
· 默认根节点名「中心主题」与默认画布名「思维导图」都判为占位（实测 2 份导图根名没改过）。

能力边界：配色/图标/关系线/边界不进正文（视觉强调不是语义）、主题的左右分支方向不保留
（布局不是语义）。

### XLSX · 表格工作簿（办公三件套的最后一件）

DOCX / PPTX / XLSX 同属 OOXML，"笔记 / 汇报 / 台账"三样正好对应办公场景里最常见的三种文件。
XLSX 的难点**不在解析而在"值"**：日期在文件里是"**序列号 + 数字格式 id**"两步表达
（`<v>45000</v>` 配 `styles.xml` 的 `numFmtId=14` 才是 `2023-03-15`）。

**所以这一档必须用 `openpyxl`，不能自己解 XML**：解错了不会报错，只会让表里静静多出一列
`45000` —— 这是**看不出来的错**，等你拿它算账才发现。docx / pptx 用库是图省事，
xlsx 用库是**不用就会错**，两者的理由不一样。

| 坑 | 处置 |
|---|---|
| 日期是序列号 | 交给 `openpyxl`；`mdtable.cell_text` 再把**零点**的 `datetime` 只输出日期 —— 否则整列日期都拖着 `00:00:00` |
| 布尔出 Python 的 `True` | 输出 `TRUE` / `FALSE`（Excel 的显示样式） |
| 只读模式下行的长度由 `dimension` 决定 | **裁掉尾部空格子**（有人把格式刷到第 16384 列，每行都拖着几十个空洞） |
| `dimension` 虚高（格式刷出来的"看起来很大"） | 全空行跳过；行上限按**迭代到的原始行**计 —— 一张声明 20 万行的表必须能在 1000 行处停下 |
| **core 时间读回来不带 `tzinfo`**（docx / pptx 带） | naive 的 `.timestamp()` 按**本地时区**解释 ⇒ 东八区下 doc_time 整整偏 8 小时。修在 `converters/office.py` 共用层（补 UTC 再算），三条通路一起受益 |
| 公式 | `data_only=True` 取**缓存值**；文件生成后从没被 Excel 打开过就**没有缓存** ⇒ 空格子（**已知边界**，不是丢数据 —— 夹具把它钉住了） |
| 合并单元格 | 只读模式拿不到 `merged_cells` ⇒ 合并区只有左上角有值。**有意取舍**：合并语义在管道表里没有标准表达，而只读模式换来"几十万行也不炸内存"。DOCX 那档做了合并检测，是因为它按段落流式读、本来就没这个约束 |
| `.xls`（97-2003）与**加密工作簿** | 都是 OLE 复合二进制（**不是 ZIP**）⇒ 在解析**之前**就分开报 `unsupported`，并给"另存为 `.xlsx`"的指引（与 `.doc` 同一处置） |

单表且表名是默认名（`Sheet1`）时**不写** `## 表名`；表名是作者起的（"7月台账"）**一定要写**
—— 那是定位信息（同 XMIND 的"单画布省略 `## 画布`"）。

### CSV / TSV · 分隔符文本表（零依赖，但最脏）

CSV 是**导出格式的默认选择**（几乎每个系统都"能导出 CSV"），所以量往往比 xlsx 还大，
脏法也更多 —— 它只有字节：没有元数据、没有类型、连"用什么分隔"都不写在文件里。

| 坑 | 处置 |
|---|---|
| **中文 CSV 大量是 GBK**（Excel 在中文 Windows 上"另存为 CSV"默认用系统 ANSI） | `utf-8-sig` → `utf-8` → `gb18030` 依次试。按 UTF-8 硬解出来是**乱码，而乱码看起来仍然像数据**（比报错难发现） |
| 分隔符可能是 `,` / `;` / `\t` / `\|` | 取**首行引号外**出现最多的候选；`.tsv` 固定制表符 |
| 引号里的逗号 | 计数时**跳过引号内** —— 否则"内容里逗号多、实际用分号分隔"的文件会判错（这是真会出现的组合） |
| 类型全丢 | **坚决不做类型推断**：`00123` 变成 `123` 是**改数据**（工号 / 邮编 / 批次号的前导零有含义），比"没识别出这是个日期"严重得多 |
| 无后缀的文件 | **不猜**"它是不是 CSV" —— 纯文本里含逗号太常见，猜错的代价是一份笔记被当成表格 |

## 7. 怎么用（CLI / MCP / 配置）

```powershell
agentmemhub feed add <文件路径> [更多路径…]     # 投喂（默认动作，可省略）
agentmemhub feed add --dry-run <路径>           # 只查重与认领，不写盘
agentmemhub feed add --force <路径>             # 同内容已投喂过也重跑（修标题/换转换器后用）
agentmemhub feed list [--status failed] [--low-quality] [--json]
agentmemhub feed show <doc_id>
agentmemhub feed retry <doc_id>                 # 重转：优先原始来源；来源不可达时**自动回落 raw/ 原件**
agentmemhub feed retry --from-raw <doc_id>      # 强制用 raw/ 原件重转（不碰原始来源）
agentmemhub feed retract <doc_id>               # **撤下**（可恢复）：删交付物+收敛投影，**原件保留**
agentmemhub feed forget <doc_id> [--purge]      # **清除登记**；--purge 才连原件一起删
agentmemhub feed lint [--json]                  # **确定性体检**；P0>0 时退出码 1
```

**批量与格式控制**（2026-10-15 新增，用户要求"用后缀控制输入、可调整支持哪些格式"）：

```powershell
agentmemhub feed formats                          # 查看当前允许的格式（含来源）
agentmemhub feed formats --set-formats ".md,.pdf,.docx"   # 运行时调整（**大小写不敏感**）
agentmemhub feed formats --set-formats clear      # 清除覆盖，回到 yaml / 默认
agentmemhub feed scan  <目录> [--no-recursive]    # **只扫描**：能投多少、被挡多少、按后缀分布
agentmemhub feed batch <目录>                     # 默认**只看不写**（等价 scan + 提示）
agentmemhub feed batch <目录> --apply             # 真的投喂
agentmemhub feed batch <目录> --apply --dry-run   # 走完整流程但一个字都不写
```

**为什么 `batch` 默认不写盘**：批量影响面大（一次可能落几百份），而用户明确要求
"未筛选的数据禁止入库" ⇒ 默认行为必须是"先看清楚再动手"。
`scan` 与 `batch` 分开，也正对应"先筛选再落库"。

**四种输入形态**（2026-10-15 用户要求明确区分；2026-10-16 补第四种 `text`）：

| 形态 | 是什么 | 注意 |
|---|---|---|
| `path` | **本机**文件路径 | 转换器自己去 `open/read` |
| `data` | **二进制内容**（调用方已 `open/read` 出来） | **必须给 `filename`** —— 扩展名是判格式的依据，裸字节没有名字 |
| `url` | 网页链接 | 取回层出网抓 |
| `text` | **正文本身** | `filename` 兼作标题；CLI 侧就是 `feed add --stdin` |

统一入口是 `service.ingest_any()`：**CLI / HTTP / 看板 / MCP 四条路走同一个门**，
各写一遍必然漂移（本项目在 wiki 上踩过"两处流程对不齐"）。

**HTTP 全套**（供数据看板直接控制，见 [`docs/API.md` §3.7](../API.md)）：
`/api/feed/formats`（查/调格式）、`/api/feed/add`（四种形态）、
`/api/feed/upload`（**二进制直传**，multipart）、`/api/feed/scan`（只读预览）、
`/api/feed/batch`（**长任务**，轮询 `/api/admin/job`），以及
`list` / `show` / `retry` / `retract` / `forget` / `lint`。

**撤下与清除的分界**：`retract` 撤下投喂内容但**原件保留** ⇒ `reconvert` 能把同一份
重新发布出来（不是单向门）；`forget` 连登记一起清除，**原件默认保留**，只有显式
`--purge` 才删。理由是同一条：`raw/` 是不可再生的那一份，其他两层都能从它重建。

**为什么不需要回收站**：交付物（kb）是**派生物**，删了随时能从原件重建 —— 这正是
三段保留的回报。而回收站恰恰会引出"扫描器漏排回收站 ⇒ 真断链被掩盖"的**双向失效**
坑（参考实现 `lint.py` 踩过，见计划 §11.4）。所以这里**直接删，不设 `.trash`**。

**投喂后要让交付物进召回面**（M2 起）：

```powershell
agentmemhub wiki --action index-pages    # 投影**所有页面根**（L2 自有 + 投喂交付物）→ units
```

`wiki --action update` / 面板增量更新也会顺带投影一次（都走
`wiki_index.project_pages`，根集合由 `page_roots()` 单点给出）。

**为什么 `retry` 要有"回落 raw"这条**：三段保留的全部意义就是"原件不可再生、其余都可重建"。
若重转只能靠 `source_ref`（用户的下载目录），用户一清理文件就再也转不了 ——
**保留下来的原件等于白存**（2026-10-12 核对投喂数据时发现该缺口）。
回落后 `source_ref` **不被改写**（仍指向原始路径），溯源不受影响。

动作既支持自然写法 `feed add X`，也支持项目惯例 `feed --action add X`；
**flag 可以夹在中间**（`feed add --force X`）—— 这一条是对 feed 特意放宽的
（argparse 默认会把 X 判成"unrecognized arguments"，见 `cli.main()` 里的说明）。

### MCP（Agent 侧，三个工具）

有了它，Agent 在会话里就能直接投喂 —— 不必让用户去切终端敲命令。

| 工具 | 用途 | 落到服务层 |
|---|---|---|
| `feed_add` | 投喂（`path` / `url` / `data` / `text` 四种形态） | `ingest_any()` |
| `feed_list` | 列素材（按状态 / 低质量筛） | `list_materials()` |
| `feed_status` | 素材库健康快照；给 `doc_id` 看单条详情 | `list_materials()` + `get_material()` + `lint(with_index=False)` |

四条实现纪律（都在 `mcp_server.py` 里守着，**各有测试**）：

1. **不依赖记忆引擎** —— 这三个工具跳过 `auth_state()` 检查。feed 是本地文件处理，
   "索引没建好就不能投喂"没有任何道理；
2. **过程日志绝不写 stdout** —— MCP 的 stdout 是 JSON-RPC **协议流**，而
   `feed/service.py` 的 `log` 默认值正是 `print`（给 CLI 用的）。照抄 CLI 写法会把
   `[+] 原件入 raw：…` 混进协议里、客户端解析直接失败。日志被**收进返回文本**，
   模型由此能看到"跑到哪一步"。有一条测试专门把 `sys.stdout` 换成捕获流来守它；
3. **`lint` 用 `with_index=False`** —— MCP 是长驻进程，不该在这里打开**真实**索引库；
   投影层是否残留请用 CLI `feed lint`（它会显式去查索引库）；
4. **只给写入与查看，不给删除** —— `retract` / `forget` 留在 CLI（后者的 `--purge`
   会删**不可再生**的原件）。低门槛写入、高门槛删除。

**新增独立、不动五工具契约**：原有五个记忆工具的名称 / 参数 / 返回格式一字未改
（Skill 侧强依赖，见 `docs/API.md` §四）。

**通知**：投喂结果按 `category="feed"` 落通知库，并按既有的 `push_when` 五开关
决定是否推微信（**不新增开关**）。默认配置下 `info=false` ⇒ 成功不打扰、失败必达
（`warning`；错误码 `crash` / `registry` 用 `error`）。
⚠️ **批量只推一条汇总** —— 一次几百份若逐条通知，标题各不相同、去重窗口失效，
用户手机会被刷爆（`test_feed_notify.py` 里有一条专门守它）。

**面板入口已落地**（2026-10-22，分支 `feat/kb-ui`）：知识库页的第三个子视图「投喂」。
第一期只读（清单 / 详情 / 格式白名单 / 体检），第二期写入与操作（四形态投喂含
multipart 上传、扫目录批量、重转 / 撤下 / 删除、格式白名单热改）。11 个 HTTP 接口
至此**全部有了前端**。

⚠️ **面板能删（含 `purge` 连原件删），MCP 仍然不能删** —— 两者约束不同，别混：
MCP 是给 Agent 的接口（低门槛、无人值守，所以只给写入与查看）；面板是人工操作，
勾选 + 二次确认之后由人负责。**不要拿 MCP 的约束去砍面板的能力。**

### 功能与入口总览（时间长了忘了就来对一遍）

| 能力 | CLI | HTTP | MCP | 面板 |
|---|---|---|---|---|
| 投喂一项 | `feed add <路径>` · `feed add --stdin` | `POST /api/feed/add`（四形态）· `/api/feed/upload`（multipart 直传） | `feed_add` | ✅ 四形态 + 多文件上传 + dry-run |
| 看投过什么 | `feed list [--status X] [--low-quality]` | `GET /api/feed/list` | `feed_list` | ✅ 清单 + 状态/低质量筛选 |
| 看单条详情 | `feed show <doc_id>` | `GET /api/feed/show/{doc_id}` | `feed_status`（传 `doc_id`） | ✅ 详情 + 跳到对应知识页 |
| 看整体健康 | `feed lint [--json]` | `GET /api/feed/lint` | `feed_status`（**`with_index=False`**） | ✅ 体检（P0/P1 分级） |
| 目录批量 | `feed scan <目录>`（只读）· `feed batch <目录> [--apply]` | `POST /api/feed/scan` · `/api/feed/batch`（长任务） | **不给** | ✅ 扫描→预览→确认投喂（接全局进度条） |
| 格式白名单 | `feed formats [--set-formats …]` | `GET`/`PUT /api/feed/formats` | 只在 `feed_status` 里显示 | ✅ 查看来源 + 热改 + 恢复默认 |
| 重转 | `feed retry <doc_id> [--from-raw]` | `POST /api/feed/retry` | **不给** | ✅ |
| 撤下 / 清除 | `feed retract` · `feed forget [--purge]` | `POST /api/feed/retract` · `/forget` | **不给** | ✅ 撤下 / 删除（勾选才连原件删） |

**MCP 为什么只给三个**：低门槛写入 + 随时自查。批量与删除影响面大
（`forget --purge` 删的是**不可再生**的原件），Agent 无人值守时不该有这种能力；
人工操作走 CLI 或面板。

### 配置项（`agentmemhub.yaml` 的 `feed` 段）

| 键 | 默认 | 作用 | 什么时候调 |
|---|---|---|---|
| `feed.db` | `database/materials.db` | 素材登记表（**独立库，不进快照**） | 换库位置（少见） |

| `feed.accept.exts` | `[]` | 允许投喂的后缀白名单；**留空 = 跟随转换器注册表** | 只想放开少数几种格式时填 |

⚠️ **这里曾有四个假开关**（`convert.llm` / `convert.ocr` / `fetch.renderer` /
`depth_default`）—— 2026-10-15 实测确认**没有任何读取点**后删除（§11 不变量 25）。
**能力做出来再加键**，别先放开关。改 yaml **不用重启**（`Config` 每次读盘），
但 MCP 是长驻进程，**换代码要重启**。

### 格式白名单的三处作用域

优先级 **运行时覆盖 > yaml > 注册表**，判定单点是 `feed/formats.py`：

| 来源 | 怎么设 | 用途 |
|---|---|---|
| **运行时覆盖** | `PUT /api/feed/formats`（写 `logs/feed_formats.json`）· `feed formats --set-formats` | 看板点选；**不改用户的 yaml** |
| **yaml** | `feed.accept.exts` | 长期口径 |
| **注册表**（默认） | 什么都不配 ⇒ 从**转换器类的 `EXTS` 类属性**收集 | 加一个转换器就自动支持 |

三条语义边界（都踩过）：**大小写不敏感**（`.PDF` ≡ `.pdf`）·
**空清单 ≠ 禁止一切**（`exts: []` 与"没配"等价，否则不配这个键的用户会被默认全禁）·
**无后缀一律放行**（URL 与无扩展名报告没有后缀可查，交给认领机制按内容判型，
判不出来照旧显式报错）。当前清单随时可查：`feed formats` 或 `feed_status`。

### 规模上限与质量降级（都是**代码常量**，不是配置）

| 常量 | 值 | 位置 | 超限后果 |
|---|---|---|---|
| `MAX_ROWS` / `MAX_COLS` / `MAX_CELL` | 1000 / 60 / 300 | `feed/mdtable.py` | **截断 + 质量 0.7**（XLSX / CSV 与 PDF / DOCX 的表格**共用同一套**） |
| `MIN_CHARS_PER_PAGE` | 50 | `converters/pdf.py` | 平均每页低于它 ⇒ 判为**扫描件**（T3c） |
| `MAX_PAGES` / `MAX_RENDER_PAGES` / `MAX_IMAGES` | 300 / 20 / 40 | `converters/pdf.py` | 页数超限不转；扫描件最多渲 20 页 |
| `MIN_TABLE_ROWS` / `MIN_TABLE_COLS` / `LOSS_TOLERANCE` | 2 / 2 / 2 | `converters/pdf.py` | 误检表格的闸门 + 剔除前的字符覆盖容忍 |
| `MAX_SLIDES` / `MAX_IMAGES` / `THIN_TEXT_RATIO` | 300 / 60 / 0.3 | `converters/pptx.py` | 只转前 N 页；有字页占比过低 ⇒ 判"基本是图"并降分 |
| `MAX_IMAGES` | 40 | `converters/docx.py` | 图片超限不再抽取 |
| `MAX_SHEETS` | 50 | `converters/xlsx.py` | 只转前 N 张工作表 + 告警 |
| `MAX_TOPICS` / `MAX_NOTE` / `THIN_TOPICS` | 20000 / 200 / 3 | `converters/xmind.py` | 主题数超限截断 |
| `MIN_ARTICLE_CHARS` | 200 | `converters/url.py` | 抽取短于它 ⇒ 报"这不是正文页"并给兜底通路 |
| `MIN_DATA_BYTES` / `MAX_BLOCKS` / `MAX_ROWS` / `MAX_COLS` / `MAX_CELL` | 256 / 4 / 200 / 12 / 80 | `feed/embeddata.py` | 内嵌数据抢救的规模闸门 |
| `TITLE_MAX` | 60 | `feed/titles.py` | 标题超长 ⇒ 截断**并记 warning**（替代标题必须让人看见） |
| `QUALITY_WARN` | 0.5 | `feed/base.py` | 低于它的已发布素材会被 `feed list --low-quality` 筛出 |

**截断是丢数据 ⇒ 必须降质量分**（不是只记一条 warning）：这样它一定会出现在
`--low-quality` 视野里，投喂通知也会升到 `warning` 级。

## 8. 并列关系与多根投影（M2）

投喂交付物与自有 wiki **并列**（用户 2026-10-10 拍板），落在**两个独立的页面根**里：

```
页面根（由 wiki_index.page_roots() 单点定义）
├── exports/wiki_work/out_l2_mimo/   ← 自有记忆长出来的（**主根**）
└── exports/wiki_work/out_feed/      ← 外部投喂的交付物（**非主根**）
```

两者都投影进 `units(source='wiki')`，靠 `origin`（`native`/`external`）区分，
一起参与召回融合（默认混排）。

**多根投影的三个安全设计**（改动 `project_pages` 前必读）：

| # | 设计 | 不这么做会怎样 |
|---|---|---|
| ① | **主根不加根标签**，其余根用目录名 | 给所有根加标签 ⇒ 主根既有 `src_id` 全变 ⇒ **库里几百个页面 unit 整体重键**，挂在它们上的价值分与 👍👎 反馈变孤儿 |
| ② | **标签按配置位置定**，不按"已存在的根" | 某个根临时缺席时另一根标签漂移 ⇒ 身份变 ⇒ 旧行被判"磁盘上已不存在"而清掉 |
| ③ | **清扫只清本轮真扫过的根** | 某个根暂时不可用（目录被移走/还没建）⇒ 它的投影**被全部删光**，等它回来再重建 |

**`wiki_path` 是绝对路径**（不是根内相对路径）：它是"两阶段召回第二阶段"的入口，
消费者（MCP 输出的 `wikiPath`）要能**直接打开**。老数据是相对路径，下一轮投影自动重写。

**为什么 `out_feed` 不放进 `out_l2_mimo`**：`wiki_aggregate` 的写盘是**整域替换**
（会 `rmtree` 掉"不属于本轮"的域目录），放进去迟早被删。两个根**互不嵌套**是结构性保证
（有测试锁）。

## 9. 日志与排查

事实流：`logs/feed.log`（JSONL，标准头五项在写入口统一补齐）。

| event | 何时 | 关键字段 |
|---|---|---|
| `feed_received` | 原件已落 raw | `doc_id` `raw_path` `bytes` `sha256` |
| `feed_converted` | 转译完成 | `converter` `title` `chars` `quality` `warnings` |
| `feed_published` | 交付物已写 kb | `kb_path` `quality` `low_quality` |
| `feed_failed` | 任一步失败（`level=error`） | `error` `error_kind` `retryable` |
| `feed_skipped` | 幂等命中，**不是失败** | `reason="duplicate"` |

**排查剧本**：

```powershell
# 这次投喂跑到哪一步就断了？
rg '"doc_id": "<doc_id>"' logs/feed.log
# 哪些失败是可以重试的？
rg '"event": "feed_failed"' logs/feed.log | rg '"retryable": true'
# 素材库里现在什么状态（落库侧，与事实流互补）
agentmemhub feed list --status failed
```

⚠️ **`error_kind` 决定处置方式**，不要只看错误文本：

| kind | 处置 |
|---|---|
| `unsupported` | 要人换格式（`.doc` 老格式、未知类型），重试无用 |
| `not_found` | 文件不在，要人给路径 |
| `encrypted` | PDF 加密，要密码（**不猜、不爆破**），重试无用 |
| `needs_ocr` | 扫描件：**原件与页面镜像已保住**，接上 T4 通路后 `feed retry` 可续跑 |
| `needs_renderer` | 扫描件 + 渲染器没装 ⇒ `uv sync --extra feed-pdf` |
| `convert` | 转换器内部失败，**可重试** |
| `needs_llm` | LLM 升级通路没接（T4 未实现）—— 目前**没有任何转换器会抛它**，留着是为了将来 T4 落地时不必改 `kind` 字典 |
| `empty` | 转出空正文，不可重试（空正文绝不进知识库） |
| `registry` / `crash` | **代码 bug**，要修而不是重试 |

体检里 `needs_ocr` / `needs_renderer` 会以 **P1 `awaiting_ocr`** 露头（不是 P0）——
能力缺口不是数据不一致，但也不该静默躺在库里；其他 `failed` 素材报 P1 `failed_material`。

---

### 确定性体检（`feed lint`）

灵感来自参考实现的 `lint.py`（它唯一的实质代码，352 行、零 LLM）：
**LLM 负责产出，脚本负责校验**。本项目此前只有 `obsidian.verify()`（依赖外部程序、
索引会过期），正因缺这一层，"顶层 index 链接指向 `.json`"那个 bug 才能活很久。

投喂链路尤其需要它：**四份东西必须严丝合缝** ——
登记表（`materials.db`）↔ 原件（`raw/`）↔ 交付物（`kb/`）↔ 投影（`units`）。
任何一处错位都是**静默的**：不报错、不让测试变红，只是"搜不到"或"点开是空的"。

| 级别 | 检查 |
|---|---|
| **P0** | 原件丢失 · 交付物丢失 · 交付物未登记 · frontmatter 缺字段 · `doc` 与登记不符 · `origin` 不是 external · **投影残留**（撤下没清干净 ⇒"删了还能搜到"）· 投影指向不存在的文件 · 投影 origin 错 · **页面根互相嵌套** |
| **P1** | 低质量（**打标但不拦发布**，§7.5）· 索引库/配置不可用（跳过而非失败） |

`P0 > 0` 时**退出码 1**，可直接当提交门槛或巡检脚本。

> **测试安全**：`run_lint` 的 `index_db` 可注入 —— 不注入就会读**真实索引库**，
> 结果依赖真实状态、测试不确定。撤下用的 `_reproject()` 则带**沙箱熔断**
> （它写的是真实索引库）：测试里会返回 `{"skipped": "test_sandbox"}`。

## 11. 不变量

1. **未知类型必须显式报错**，绝不静默跳过（本项目踩过"未知 source 静默跳过"的坑）。
2. **原始件永不丢**：认领失败、转译失败都要先落 `raw/` —— 否则将来补上转换器也无法重转。
   **推论：重转不得依赖原始来源可达** —— `retry` 在来源消失时必须回落到 `raw/` 原件
   （`reconvert()`），否则"原件保留"只是摆设。
3. **`kb` 文件路径只由 `doc_id` 派生**（`<doc_id>.md`）—— 投影的 `src_id`/`seq` 由路径派生，
   路径必须稳定；可变的标题放 frontmatter。
4. **`doc_time` 是文档自身时间**，不是投喂时刻（与 `distill._origin_time` 同语义）。
5. **`FeedDocument` 是唯一契约**：下游只认它，不为某种格式开后门。
6. **转译层的对外副作用必须可审计**：每个事件进 `logs/feed.log`，`depth` 要算对
   （隔了包装层必须 +1，否则行号恒等、字段作废）。
7. **质量自评低于阈值仍然发布，但必须打标**（`feed list --low-quality` 可筛）——
   静默失真比"拒收"更危险（`docs/feed-adapter-plan.md` §7.5）。
8. **页面根只由 `page_roots()` 定义**（`wiki_index.py`）—— CLI / wiki 管道 / 面板
   各写一份必然漂移；两个根**互不嵌套**（否则一方的整域替换会毁掉另一方）。
9. **多根投影的三条身份纪律**（见 §8）：主根不加标签、标签按配置位置定、
   清扫只清本轮真扫过的根。违反任一条的后果都是**数据损失**（重键 / 投影错乱 / 误删）。
10. **`wiki_path` 是绝对路径** —— 它是两阶段召回第二阶段的入口，必须是"能直接打开"的
    形态，否则消费者拿到也读不了。
11. **派生物不需要回收站**：交付物（kb）与投影都能从原件重建，所以撤下**直接删**；
    只有 `raw/` 是不可再生的那一份 —— `forget` 默认保留它，`--purge` 才删。
12. **碰真实路径的出口必须有沙箱熔断**：`_reproject()` 写的是真实索引库，
    测试沙箱下必须跳过（本项目 2026-09-26 的事故就是"测试经真实路径改了真实产物"）。
13. **格式分派必须"先探再派"，且判据客观可算**：不许看文件名/来源猜类型。
    ⚠️ 探针的**读取顺序**也是不变量的一部分：加密必须先于页数（否则加密档表现为崩溃
    而不是可处置的 T3d）。**判据可单独测**（`probe()`/`route()` 是纯函数）——
    端到端测试只能反推判据，测不出"判错了哪一条"。
14. **不可再生的中间产物要在报错之前先落地**：T3c 是"**先渲染进 `mirror/`，再**抛
    `needs_ocr`" —— 素材进来一趟，原件与可见内容都该留下；反过来的话，
    OCR 通路接上后又要重新抓一次原件。
15. **能力缺口与数据损坏必须分开报**：`needs_ocr`/`needs_renderer` 是**能力没接**
    （原件都在），所以体检里是 P1；数据不一致（原件丢了、交付物没了、溯源断了）才是 P0。
    混在一起会让"体检红了"失去指向性。
16. **任何"从正文里删东西"的操作都必须先证明不丢字**。表格区域剔除是最典型的例子：
    它是从正文里**删**字符，所以必须先做覆盖校验（`剔除后 + 表格内容 ⊇ 原页字符`），
    并且**校验两端必须同源**（拿两个引擎的输出比，光空格差异就会让校验永远不敢放行）。
    校验不过就**放弃剔除**（宁可重复），因为"重复很难看、丢字是数据事故"。
    ⚠️ 2026-10-15 真实素材事故：一行代码被误检成"1 行 2 列"表格，照单全收 ⇒
    那行字**从知识库里永久消失**（连"语"字都被吞了）。
17. **标题是"替代品"时必须让人看见**。标题四个来源都可能不可用（元数据被写坏、
    文档没用样式、首段过长、文件名是「文字文稿1」）；用替代来源时**限长 + 记 warning**，
    绝不悄悄给一个像是原文的标题 —— 那会被当成文档真标题一路用下去。
    判据单点在 `feed/titles.py`（PDF/DOCX 共用），改判据要同时想两边的后果。
18. **相对路径是一等公民，不许硬编码 `https?://`**。图片、链接、资源引用在真实文件里
    大量是相对的 —— 本地另存的网页尤其如此。一个"只匹配绝对 URL"的正则会让
    整类素材静默丢图（M3 起就埋着，直到 2026-10-15 拿本地 HTML 测才暴露）。
19. **覆盖率不等于信息量**。质量自评按"抽出内容 / 可见文本"算，会给"只有字段标签的空壳"
    打满分（抽取确实覆盖了全部可见文本）。所以自评之外还要有**形态判据**
    （`looks_like_label_shell`）去识别"看起来抽全了、其实是空的"，
    否则指标越正确、问题越隐蔽。
20. **格式白名单必须跟随注册表，不能人工维护第二份清单**。`feed/formats.py` 从
    转换器类的 `EXTS` 收集默认值 —— 两处清单必然漂移，而"明明支持却投不进来"
    是最难查的那类问题。
    ⚠️ 后缀常量必须是**类属性**：写成模块级常量时注册表收集不到，白名单会静默退化成
    "什么都不许投"（实测第一次跑就撞上）。
21. **批量入口默认不落盘**。批量投喂影响面大（一次几百份），而"投进去容易、清干净难" ——
    所以默认是"只扫描列清单"，必须显式 `--apply` 才写。这与"先筛选再落库"是同一条纪律。
22. **"值"错了比"结构"错了更难发现 —— 能算出正确值就别自己算**。XLSX 的日期是
    "序列号 + 数字格式 id"两步表达；自己解 XML 不报错，只让表里静静多出一列 `45000`。
    凡库能给出**语义化值**（日期 / 布尔 / 类型）的地方，都不该为"少一个依赖"手写解析。
    同理，**读回来的时间必须确认时区**：OOXML 的 W3CDTF 是 UTC，但 `openpyxl` 读回来
    **不带 `tzinfo`**（`python-docx` / `python-pptx` 会保留）—— naive 直接
    `.timestamp()` 按**本地时区**解释，东八区下整整偏 8 小时。判据单点在
    `converters/office.py`（三条通路共用）。
23. **表格类格式共用一套渲染与规模上限**（`feed/mdtable.py` 的 `table_md` +
    `MAX_ROWS` / `MAX_COLS` / `MAX_CELL`）：PDF / DOCX / XLSX / CSV 四条通路都走它。
    各写一份的结果是"同一张表从 csv 进来和从 xlsx 进来长得不一样、截断点也不一样"。
    **截断是丢数据 ⇒ 必须降质量分**（不是只记一条 warning）。
24. **不做类型推断**。CSV 里 `00123` 是**字符串** —— 把前导零"美化"掉就是**改数据**，
    比漏识别严重得多，因为它在下游看起来完全正常（工号 / 邮编 / 批次号都会中招）。
    同理，CSV 的编码必须按 `utf-8-sig → utf-8 → gb18030` 依次试：中文 Excel 导出的
    CSV 默认是 GBK，按 UTF-8 硬解出来是**乱码，而乱码看起来仍然像数据**。
25. **加配置键必须与"写进 `agentmemhub.yaml.example`"同一步**。`check_config_keys.py`
    只扫 example 与本地 yaml 里出现过的键 —— **不在这两处的键不在它视野内**。
    2026-10-15 实测：`feed` 段里那四个假开关（`convert.llm` / `convert.ocr` /
    `fetch.renderer` / `depth_default`）长期存在而审计报"0 僵尸键"，原因正是
    example 里**根本没有 `feed` 段**。已删键并把真实的 5 个键补进 example ——
    **能力没做出来之前，不要先在这里放开关**（配了不生效比没有这个键更坏）。
26. **新入口必须薄封装服务层，且不污染协议流**。CLI / HTTP / MCP 三处都调
    `feed/service.py` 的**同一批函数**（`ingest_any` / `list_materials` /
    `get_material` / `lint`…）—— 各写一份逻辑必然漂移。两条推论：
    · **stdio 的 stdout 只许放协议**：MCP 那层把 feed 的过程日志**收进返回文本**
      （`log` 默认 `print` 是给 CLI 场景的）；
    · **新入口不许改原有契约**：feed 三个工具是新增，五个记忆工具的 schema 与
      返回格式一字未改（Skill 侧强依赖）。
27. **通知是旁路，且批量不许逐条推**。投喂结果按 `category="feed"` 复用既有
    `push_when` 五开关（**不新增键**）：成功 `info`（默认不推）、低质量与失败
    `warning`、代码 bug（`crash` / `registry`）`error`。**批量只在结束时推一条汇总** ——
    逐条推时标题各不相同 ⇒ 去重窗口失效 ⇒ 手机被刷爆。
    通知层的任何异常都必须吞掉：推送通道挂了不能让投喂失败（`feed/notify.py`）。
